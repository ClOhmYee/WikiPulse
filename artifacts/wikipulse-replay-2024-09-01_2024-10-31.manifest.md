빈 디렉터리를 줬다. 판단 근거: 89일 × 567 MB(user만) ≈ **50 GB · 12~22시간**이라 기한 안에
불가능하고, §11 실측상 리플레이에서 조회수가 탐지에 기여한 적이 없다(`-85`: 탐지 240여 건이

🔴 **`views` 값을 정확히 적는다 — "0 으로 합성" 도 "None 으로 치환" 도 하지 않았다.**
`-58` 의 `join_windows` 는 full outer join 이라 조회 적재본이 없으면 `views=0` 을 낸다.
이건 **기존 develop 계약이고 이번 Story 에서 손대지 않았다.** `bulk_replay` 는 소스가 준
값을 그대로 `PageWindow` 로 넘긴다. 그 0 으로 만든 기준선은 `view_ewma=0` 이 되고,
`detect._view_signal` 이 `view_ewma<=0` 에서 `(None, None)` 을 돌려 조회수 관문이 안전한
쪽으로 닫힌다.

→ **결과: 조회수 경로가 한 번도 발동하지 않았다.** 실제로 이 데이터셋의
`spike.view_ratio` 는 6,614행 **전부 NULL** 이다. **view-only spike(읽히기만 하고 편집은
안 느는 기존 문서, 예: Strait of Hormuz 형)는 이번 데이터셋에서 잡히지 않는다.**
화면에서는 `cluster_member.views=null`, `completeness='pending'` 으로 나타난다.

## 5. 실행 명령 (재현 순서)

```bash
export CONTACT_EMAIL="<연락처>"            # Wikimedia UA 규정
export DATABASE_URL="postgresql://wikipulse:wikipulse@localhost:5432/wikipulse_replay"
cd data-pipeline

# 1) 편집 덤프 적재 (3개월)
python -m batch.ingest --wiki enwiki --range 2024-08     # 2024-09, 2024-10 도 같은 식

# 2) Historical Window (조회수 없이 — 빈 디렉터리)
mkdir -p data/pageview-empty
python -m batch.historical_windows_ingest \
    --edits out/enwiki/2024-08 --views data/pageview-empty \
    --out data/baseline-input/enwiki/2024-08

# 3) 기준선 (warm-up 구간만)
python -m spike.baseline_sink --input data/baseline-input/enwiki/2024-08 --as-of 2024-08-31

# 4) bulk 리플레이 (chunk = 월. --since/--until 로 일 단위 분할 가능)
python -m spike.bulk_replay --windows data/baseline-input/enwiki/2024-09 \
    --since 2024-09-01 --until 2024-09-30 --state data/bulk-state.json
python -m spike.bulk_replay --windows data/baseline-input/enwiki/2024-10 \
    --since 2024-10-01 --until 2024-10-31 --state data/bulk-state.json

# 5) 클러스터 (전 구간 한 번에, detected_at 오름차순)
python -m cluster.driver --dsn "$DATABASE_URL" --source replay
```

### 새로 만든 것: `spike/bulk_replay.py`

판정 B — reader(`-58` 산출물)·runtime·sink 가 이미 다 있었고 **CLI 진입점만 없었다**.
`spike/replay.py` 는 `--title` 로 준 문서만 재생하는 회귀 검증 도구라 60일 연속
리플레이에 쓸 수 없다. 새 모듈은 판정 로직을 한 줄도 갖지 않는다.

### `detector.may_spike()` — 무손실 사전필터

기준선을 읽기 전에 "어떤 기준선이 와도 급증일 수 없는" 윈도우를 거른다. 임계 상수를
복제하지 않고 같은 파일의 상수를 본다. 실데이터에서 **154,064 → 289 윈도우(0.19%)** 로
기준선 왕복을 줄였다.

무손실 증명 (`tests/test_bulk_replay.py`, 17개 통과):

| 층위 | 대조 | 결과 |
| --- | --- | --- |
| 격자 전수 | 임계 경계 포함 윈도우 280 × 기준선 7 = 1,960 조합, 급증 672건 | 유실 0 · 판정 튜플 불일치 0 |

## 10. 알려진 한계

🔴 **1-member 100% · edge 0 은 데이터 부족이나 pageview 문제가 아니다.**
Clickstream / 비-seed membership 을 **생산 경로에 붙이는 배선이 아직 없어서**다.
조회수를 받아도, 구간을 늘려도 이 두 숫자는 안 바뀐다. 후속 Story 범위다.

| 항목 | 상태 | 원인 |
| --- | --- | --- |
| multi-member cluster | ❌ 전부 1-member (6,614/6,614) | **Clickstream 이웃이 생산 경로에 배선되지 않았다** — `cluster/driver.py` 의 `build_snapshot_at` 이 `neighbors={}` 로 고정해 넘기고, `load_pages_by_title` 은 없으며 `load_creation_dates` 는 `NotImplementedError`, CLI 에 `--clickstream` 인자도 없다 |
| `cluster_edge` | ❌ 0건 | 같은 원인 — 이웃이 없으면 간선도 없다 (`cluster_edge` 는 Clickstream 이웃에서만 생긴다) |
| 비-seed 멤버(`-77` 규칙) | ❌ 미구현 | 규칙만 확정, `snapshot.py` 는 여전히 생성일 창 게이트 |
| `issue_report`(AI 요약) | ❌ 비어 있음 | 쓰는 코드가 저장소에 없음 (WP-68) |
