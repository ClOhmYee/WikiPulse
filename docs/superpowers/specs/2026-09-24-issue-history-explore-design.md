# 이슈 탐색: 대표 문서별 검색과 시점 타임라인

- 날짜: 2026-09-24
- 기준: `origin/develop` `5d9768d`
범위: 검색·상세의 **읽기 전용** 확장. 클러스터링·적재·기존 피드·펄스맵·DB 데이터는 변경하지 않는다.

## 의도와 성공 조건

사용자는 대표 문서 A를 검색했을 때 날짜마다 반복된 클러스터 카드 대신 A의 기록을 한 건으로 찾고, 상세에서 각 시점의 클러스터를 이동하며 당시 구성 문서 B·C·D, 요약, 종목을 확인하고 싶다. 기존 MVP가 깨지면 안 되므로 운영 기본 화면은 그대로 유지하고, 새 기능은 검증 후에만 켠다.

성공 조건:

1. 검색어가 없거나 기능 플래그가 꺼져 있으면 현재 탐색·상세 화면과 API 동작이 그대로다.
2. 플래그가 켜지고 대표 제목으로 검색하면 모든 완료된 과거 스냅샷에서 `issue_key`별 결과가 한 건씩 나온다. 결과의 발생 횟수·최초/최근 시점은 실제 기록과 일치한다.
3. 결과에 들어가면 시점별 이슈 ID를 선택할 수 있고, 각 선택은 기존 `/issues/{id}` 상세를 그대로 연다. 구성 문서·요약·종목을 다른 시점에서 빌려오지 않는다.
4. 읽기 전용 API만 추가한다. 스키마 변경, 데이터 재처리, 운영 배포는 이 작업의 일부가 아니다.

## 검토한 접근

- **현재 페이지에서 프론트만 묶기:** 가장 작지만 현재 20건 밖의 과거 기록을 찾지 못한다. 요구사항을 충족하지 못해 제외.
- **새 read-only 검색/이력 API + 기존 상세 재사용 (채택):** 전역 검색과 날짜 이동을 제공하면서 기존 계약과 데이터를 보존한다.
- **사건 ID/에피소드 테이블 신설:** 동일한 현실 사건을 더 잘 구분할 수 있지만 데이터 모델·파이프라인 변경 및 백필이 필요하다. MVP에는 과하다.

## 데이터 의미와 한계

`issue_cluster`의 한 행은 한 스냅샷의 클러스터이고 ID는 시점마다 다르다. `issue_key`는 `source:wiki:대표 문서`로 생성되어 시점 간 연결에 쓸 수 있지만 **실제 사건의 영구 ID는 아니다**. 따라서 UI는 “같은 대표 문서의 기록”으로 표시하고 “동일 사건”이라고 단정하지 않는다. 대표 문서가 바뀌면 별도 검색 결과가 될 수 있고, 같은 대표 문서의 다른 사건이 한 기록 묶음에 함께 나올 수 있다. `issue_key IS NULL`인 옛 행은 서로 묶지 않고 각각 한 건으로 취급한다. `live`와 `replay`는 `issue_key`가 달라 별도 결과이며 출처를 명시한다.

이번 검색 대상은 **대표 제목**이다. B·C·D처럼 구성원으로만 포함된 문서 제목 검색, 한국어 별칭 검색, 사건 의미 기반 통합은 제외한다. 시점은 날짜만으로 합치지 않고 원본 `snapshot_ts`까지 표시한다. 같은 날 여러 스냅샷이 있을 수 있기 때문이다.

## API와 조회

기존 `GET /api/v1/issues`, `GET /api/v1/issues/{id}`, 버블맵 API는 변경하지 않는다.

1. `GET /api/v1/issues/history/search?q=&source=&offset=&limit=`: 대표 제목 부분검색. `q`는 trim 후 1~200자이며 비어 있거나 초과하면 400이다. `%`, `_`, `\`는 와일드카드가 아닌 리터럴로 취급한다. `source`는 기존 `live`/`replay` 검증, `offset`은 0 이상, `limit`은 1~100이다. `status <> DISCARDED`이고 `cluster_snapshot`에 등록된 완료 스냅샷만 사용한다. 결과는 `issue_key`별 한 건(키가 없으면 ID별)으로 집계하고, 최근 시점 내림차순·대표 ID 오름차순으로 안정 정렬한다. 각 결과는 대표 제목, 출처, 최신 이슈 ID/상태/점수, 최초·최근 시각, 발생 횟수를 담는다. 페이지네이션은 **묶은 결과** 기준이다.
2. `GET /api/v1/issues/{id}/history?offset=&limit=`: 해당 ID의 `issue_key`를 찾아 같은 키의 완료·비폐기 시점들을 최신순으로 반환한다. 키가 없으면 해당 ID만 반환한다. 각 항목은 이슈 ID, `snapshotTs`, 상태, 점수, 구성 문서 수를 담으며 페이지네이션한다. 없는/폐기된 기준 ID는 기존 상세와 같이 404다.

읽기 쿼리는 기존 `issue_cluster(issue_key, snapshot_ts)` 인덱스를 우선 활용한다. 새 인덱스·마이그레이션은 미리 넣지 않는다. 검색 성능을 실제 데이터 규모에서 측정해 부족할 때 별도 변경으로 다룬다.

## 프론트엔드 흐름

빌드 플래그 `VITE_ISSUE_HISTORY_ENABLED`의 기본값은 꺼짐이다.

- 꺼짐: 현재 페이지 제목 필터, 목록 페이지네이션, 상세 화면이 그대로 동작한다.
- 켜짐 + 검색어 없음: 기존 최신 LIVE/replay 목록 그대로.
- 켜짐 + 검색어 있음: 서버의 묶음 검색으로 전환한다. 카드에는 대표 제목, 출처, 최초/최근 시각, 발생 횟수를 표시한다. 검색 결과의 페이지네이션도 서버가 반환한 묶음 수를 따른다. 이 모드에서는 기존의 “현재 스냅샷 분석 상태” 필터를 숨기고 그 선택을 적용하지 않는다. 저장 버튼은 기존 ID 단위 저장과 혼동되지 않도록 묶음 카드에 넣지 않는다. 시점 상세에서는 기존 저장 기능이 그대로다.
- 검색 결과 클릭: 최신 시점 ID의 기존 `#/issues/{id}`로 이동한다. 상세 상단에 “이 대표 문서의 기록” 목록을 추가하고 시점 선택 시 해당 ID로 이동한다. 구성 문서·리포트·주식 섹션은 기존 상세 데이터에만 의존한다.
- 검색/이력 조회 실패: 기존 데이터를 추측해 합치지 않는다. 새 기능 영역에 오류·재시도 또는 이력 사용 불가 안내를 표시한다. 기존 상세 내용은 계속 표시한다.

## 검증과 롤백

격리 브랜치에서 먼저 백엔드 API 계약·SQL 통합 테스트와 프론트 데이터 계약·화면 테스트를 추가한다. `issue_key` 반복, 서로 다른 키/출처, NULL 키, 폐기·미완료 스냅샷, 같은 날짜의 다중 시점, 페이지 경계, 검색 특수문자, 이력 API 실패를 검증한다. 기존 테스트와 빌드를 통과시킨 다음, 대표 사례(예: Odyssey)의 실제 검색 결과·발생 횟수·날짜별 상세 링크를 읽기 전용으로 확인한다.

롤백 순서: (1) 프론트 빌드 플래그를 끄고 기존 탐색 화면으로 복귀, (2) 문제가 계속되면 직전 검증된 배포 버전으로 되돌리거나 변경 MR만 revert. 새 API는 additive이고 DB 변경·재처리가 없으므로 데이터 롤백이 필요하지 않다. 운영 플래그 활성화와 배포는 별도 승인 및 프론트 담당자 검토 후 진행한다.

## 비범위

클러스터링 품질 개선, 서로 다른 대표 문서의 사건 통합, 구성원 문서 검색, 새 AI 요약 생성, 기존 이슈 ID 변경, 백필·삭제, 운영 설정 변경은 하지 않는다.
