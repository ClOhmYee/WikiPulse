# 온보딩 트러블슈팅

## 1. 루트 앱이 열리고 온보딩이 보이지 않는다

**증상**

- `npm run dev`를 실행했는데 다른 WikiPulse 화면이 열린다.
- `frontend`를 수정했지만 브라우저에 반영되지 않는다.

**원인**

저장소 루트의 Next.js 애플리케이션과 `frontend/`의 Vite 온보딩은 별도 앱이다.

**해결**

```powershell
npm.cmd --prefix frontend run dev
```

Vite가 출력한 주소와 현재 브라우저 주소가 같은지 확인한다. 설치와 빌드도 같은 방식으로 `--prefix frontend`를 사용한다.

## 2. 수정 내용이 바로 보이지 않는다

**증상**

- 소스는 바뀌었지만 점 크기, 간선, 셰이더 변화가 이전 상태처럼 보인다.

**원인**

Vite HMR은 대부분 반영하지만, 기존 WebGL 컨텍스트의 material·buffer 상태나 오래 열린 탭 때문에 시각 결과가 남아 보일 수 있다. 혜성 꼬리 작업 중에도 새로고침 뒤에야 변경이 확인된 사례가 있었다.

**해결**

1. 먼저 브라우저를 한 번 전체 새로고침한다.
2. 그래도 같으면 Vite 터미널의 compile error와 현재 접속 포트를 확인한다.
3. WebGL 변경은 첫 장면부터 다시 진입해 전환을 재현한다.

새로고침 전 화면만 보고 코드가 실패했다고 판단하지 않는다.

## 3. 배경별 꼬리가 안 보이거나 별보다 커진다

**경과**

- 점 두 개가 희미하게 따라오는 방식은 꼬리로 읽히지 않았다.
- 강도를 올리자 꼬리 시작점이 별 머리보다 커지고 화면이 과해졌다.
- 스크롤 방식이 바뀔 때 잔상 길이와 속도 관계도 불안정했다.

**최종 해결**

혜성 꼬리, 고스트 copy, 잔상 shader를 모두 제거했다. 현재는 signed scroll velocity가 별 볼륨의 회전 방향과 속도만 바꾼다.

**회귀 확인**

- 정지 상태의 별이 깨끗한 원형인지 확인한다.
- 빠른 정·역방향 전환에서 두꺼운 광선이나 점 복제 흔적이 없는지 확인한다.

## 4. 첫 장면 간선이 너무 많거나 잘 안 보인다

**원인**

연결 거리 threshold는 밀도와 구성 자체를 바꾸고, opacity는 연결 구조를 유지한 채 가시성만 바꾼다. 두 값을 동시에 조정하면 원하는 원인을 판단하기 어렵다.

**현재 기준**

- `connectWithinDistance(..., 0.51, ...)`
- seed `0xc4885e62` 기준 953개
- 첫 장면 opacity `0.145`

**해결 순서**

1. 간선 수가 적절하고 흐리기만 하면 `edgeOpacity[0]`만 조절한다.
2. 구조가 복잡하면 거리 `0.51`을 조절하고 실제 edge count를 다시 확인한다.
3. 장면 2에는 간선이 없어야 한다.

## 5. 1→2 또는 2→3 전환 중 검은 간선이 나타난다

**증상**

청록 배경 위에 잠깐 검은 선이 생겼다가 사라진다.

**원인**

간선을 fade할 때 RGB 자체에 낮은 intensity를 곱하면 색이 검정에 가까워진다. 투명한 선이 아니라 어두운 선이 렌더된 것이다.

**해결**

- line color attribute를 RGB 3개가 아닌 **RGBA 4개**로 유지한다.
- `lineColors`는 `MAX_EDGES × 8`, buffer attribute item size는 `4`다.
- RGB에는 원래 white/teal/gold 값을 기록하고 fade는 alpha에만 적용한다.

**회귀 확인**

1→2→3과 역방향을 천천히 반복해 검은 선이 한 프레임도 나타나지 않는지 확인한다.

## 6. Track 글로우의 속도·동기화·개수를 바꾸고 싶다

**현재 기준**

- 주기 `0.7s`
- 대상 38개
- 모든 대상이 같은 위상으로 동기화
- `sourceIndex = glowIndex × 4`

**주의**

글로우 개수를 줄이기 위해 `clusterCount`나 클러스터 인덱스를 바꾸면 다음 장면의 군집 구성까지 깨진다. 글로우 sampling만 변경하고, 150개 클러스터 소유권은 유지한다.

**회귀 확인**

- 장면 2에서 글로우 노드가 동시에 밝아지고 어두워지는지 확인한다.
- 장면 3으로 이동했을 때 글로우하지 않던 노드도 같은 클러스터로 모이는지 확인한다.

## 7. 장면 2에서 군집이 평면처럼 보이거나 마우스를 피한다

**원인**

- 1→2의 기준 위치를 다른 평면 좌표로 두었거나 z값을 축소했다.
- 장면별 `interactionStrength`에서 1·2장면 값이 0이 아니다.

**현재 기준**

- 장면 0과 1은 같은 3D 구 좌표를 사용한다.
- 중간 구간에만 확산·회전·깊이 burst를 더한다.
- `interactionStrength = [0, 0, 0.38, 0.3]`이므로 1·2장면에는 국소 반발이 없다.

포인터에 대한 damped 전체 회전은 유지한다.

## 8. 장면 3의 주변 노드가 사라지거나 4에서 새로 생긴 것처럼 보인다

**원인**

비클러스터 노드의 장면 3 scale/opacity가 너무 낮거나, 장면 4에 별도 그래프 노드를 생성했을 가능성이 있다.

**해결**

- 장면 3에서 인덱스 `150..349`를 주변 3D 필드로 유지한다.
- 장면 4에서는 동일 인덱스가 `150..289` 가격선, `290..349` 거래량으로 이동하게 한다.
- 새 Points geometry를 만들지 않는다.

## 9. 장면 4가 좁고 납작하거나 매핑 선이 한곳에 몰린다

**경과**

- 상하 배치와 우측 1/3 배치는 데스크톱에서 두 도형을 모두 작게 만들었다.
- 가장 가까운 점만 연결하자 시작점과 도착점이 한 구역에 몰렸다.

**최종 해결**

- 데스크톱은 우측 약 2/3에서 클러스터와 그래프를 좌우 배치한다.
- 그래프 폭은 `4.15`, 시작 x는 `2.4`다.
- 클러스터 경계 후보를 한 축으로 정렬하고, 가격선의 `[8, 26, 44, 62, 82]%` 지점에 다섯 선을 분산한다.
- 모바일에서만 상하 배치를 사용한다.

레이아웃을 수정할 때 화면 점유율만 보지 말고 두 그룹의 **시각 높이**, bridge gap, 카피와의 충돌을 함께 확인한다.

## 10. 가격 노드가 이동 시작과 동시에 gold가 된다

**원인**

노드 위치와 색상이 같은 accelerated transition progress를 사용하고 있다.

**해결**

위치 보간은 그대로 두고 가격 색상에만 별도 progress를 적용한다.

```js
colorProgress = clamp(
  (rawSegmentProgress - MATCH_PRICE_COLOR_START)
    / (1 - MATCH_PRICE_COLOR_START),
  0,
  1,
)
```

현재 `MATCH_PRICE_COLOR_START`는 `0.68`이다. 거래량의 teal 전환 시점과 노드 이동은 지연시키지 않는다.

## 11. 2–4장면 제목이 첫 장면 W보다 아래에서 시작한다

**원인**

아이콘·폰트·line-height 때문에 CSS로 계산한 컨테이너 top과 실제 `W` 글리프 line box의 시작점이 다르다. 웹폰트 로딩 후에도 값이 바뀔 수 있다.

**해결**

- `heroWordmarkRef`의 `offsetTop`을 stage까지 누적한다.
- 결과를 `--scene-wordmark-top` CSS 변수로 기록한다.
- `ResizeObserver`, 창 resize, `document.fonts.ready`에서 다시 측정한다.

고정 pixel `top`으로 덮어쓰면 다른 화면 높이에서 다시 어긋난다.

## 12. 첫 장면 영문 설명의 stocks가 다음 줄로 내려간다

**해결**

721px 이상에서는 hero body에 `white-space: nowrap`을 적용한다. 모바일에서는 긴 문장이 화면을 넘지 않도록 줄바꿈을 허용한다. 문장을 줄이기 전에 실제 breakpoint와 텍스트 영역 폭을 확인한다.

## 13. 배경 점 일부만 크게 만들 수 없다

**원인**

기본 `PointsMaterial`의 `size`는 draw 전체에 공통이다.

**해결**

별 데이터를 z 조건으로 둘로 나누고 두 개의 geometry/draw를 사용한다.

- 먼 leftward subset: `0.06`
- remaining subset: `0.054`

별의 개수·색·회전 로직은 공유하고 material size만 다르게 한다. 의미 노드 수와 섞지 않는다.

## 14. WebGL이 없거나 컨텍스트가 손실된다

**현재 대응**

- 초기 `canvas.getContext("webgl2") || canvas.getContext("webgl")`로 지원 여부를 확인한다.
- Canvas의 context-lost callback이 `webglAvailable`을 false로 바꾼다.
- `StaticFallback`은 같은 네 장면 카피를 일반 DOM으로 제공한다.

**회귀 확인**

폴백에서도 제목, 부제, 설명의 순서와 의미가 유지되고 자연스럽게 세로 스크롤되는지 확인한다.

## 15. 빌드는 성공하지만 청크 크기 경고가 나온다

**현상**

`npm.cmd --prefix frontend run build`가 성공한 뒤 JavaScript 청크가 500 kB를 넘는다는 Vite 경고가 나온다.

**판단**

Three.js와 R3F를 포함한 현재 구조에서는 예상 가능한 비차단 경고다. 빌드 실패로 취급하지 않는다. 실제 배포의 초기 로딩 요구사항이 정해지면 다음을 검토한다.

- 온보딩 라우트 또는 `NodeField` 지연 로딩
- vendor chunk 분리
- 정적 폴백을 먼저 보여준 뒤 WebGL hydration
- 번들 분석 후 사용하지 않는 의존성 제거

## 16. 빌드는 통과하지만 모션이 어색하다

빌드는 문법·번들 가능 여부만 확인한다. GPU 기반 깊이, 겹침, blur, 속도감은 시각 QA가 필요하다.

### 최소 수동 QA 매트릭스

| 환경 | 확인 항목 |
| --- | --- |
| 데스크톱 마우스 | 장면 1·2 회전, 장면 3·4의 제한적 반발, 카피 비충돌 |
| 트랙패드/휠 | 한 제스처 한 장면, 잠금 종료 후 다음 입력 허용 |
| 모바일 터치 | 수직 swipe, 버튼, 장면 4 상하 구성, 텍스트 wrapping |
| 키보드 | Arrow/Page/Space/Home/End와 focus 표시 |
| 역방향 | 4→3→2→1에서 색·간선·소유권이 자연스럽게 복원 |
| reduced motion | 즉시 snap, 정지된 별·노드, 유지되는 정보 |
| WebGL 폴백 | 네 장면 카피의 읽기 순서와 접근 가능성 |

## 17. 변경 후 확인 명령

```powershell
npm.cmd --prefix frontend run build
```

현재 `frontend/package.json`에는 `lint`나 `test` 스크립트가 없다. 따라서 빌드 성공을 테스트 완료로 표현하지 말고, 위 수동 QA 결과와 구분해서 기록한다.
