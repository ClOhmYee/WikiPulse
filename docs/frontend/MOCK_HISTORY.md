# 연간 Wikipedia 목데이터

데이터 기준일: 2026-09-10 · 계약 갱신: 2026-09-15. Jira: WP-78, 95~98.

## 실행과 범위

`frontend/.env`의 `VITE_DATA_SOURCE=mock`으로 실행한다. 기간은 **2025-09-01~2026-09-10**, 매일 09:00 KST 스냅샷 375개다. 자동으로 오늘까지 늘어나지 않는 고정 데이터셋이며, 날짜·주제·수치는 실행할 때마다 같다. 사용자 요청의 "이번년"보다 구체적인 날짜 범위를 우선했다.

- **실제 문서 287개, 주제 36개, 월별 리포트 468개, 날짜별 클러스터 리포트 9,698개, 구성 증권 102개**를 제공한다. 현재 지도에는 공유 문서를 포함해 318개 문서 노드가 있다. AI·반도체·에너지·바이오·무역·여행·문화·스포츠 등을 포함한다.
- 실제 Wikipedia 문서 제목, 페이지 ID, 원문 URL, 최초 리비전 시각/ID를 `frontend/src/data/mock/fixtures/sources.json`에 보관한다. 영문 문서의 한국어 이름과 설명은 직접 작성한 표시용 문구다. 본문을 복제하지 않는다.
- **실제 2025~2026년 뉴스 또는 편집 기록을 재생하는 데이터가 아니다.** 날짜별 급증·주제 묶음·클러스터 상태·조회수·간선·리포트·종목 관계·주가는 모두 합성이다. 2025/2026년 행사 문서와 오래된 배경 문서를 함께 쓴다. 문서가 그해 처음 생성됐다는 뜻도 아니다.
- 실제 문서 생성일보다 앞선 스냅샷에는 해당 문서를 넣지 않는다.
- 종목은 출처 목록에 있는 **현재 Nasdaq-100 구성 증권 전부**를 사용한다. Alphabet의 복수 주식 클래스 등으로 증권 수와 100개 기업은 일치하지 않을 수 있다. 현재 목록을 전체 기간에 고정 적용하며, 과거 편입·퇴출이나 당시 상장 여부를 재현하지 않는다.

## 데이터 흐름

```text
검증한 Wikipedia 문서 목록
  → 문서 ID·날짜로 재현 가능한 합성 활동 수치
  → 사람이 지정한 주제별 문서 묶음 + 급증 씨드
  → 동일 노드 집계로 클러스터 지도와 리포트 생성
  → 리포트의 주제와 현재 Nasdaq-100 사업 영역 연결
```

`history.js`가 공통 생성 규칙이다. 동일 문서·날짜의 편집수/기준량/조회수는 모든 클러스터에서 동일하며 리포트는 그 노드 수치를 합산한다. 합성 급증 씨드는 편집 배수 4 이상, HOT은 클러스터 편집 배수 6 이상이다. 프로덕션의 z-score 판정을 대신하는 알고리즘이 아니다. 공통 크기 척도는 `min(1, 편집 배수 / 12)`다.

`topics.js`는 수작업 주제, 문서, 종목의 연결 목록이다. 문서 쌍 간선은 시연용 토폴로지이고 Clickstream 필드 형식을 사용하지만 실제 덤프 측정값이 아니다. `evidence.label`에 합성임을 표시한다. 소속만으로 실제 관계를 입증하지 않는다.

`catalog.js`의 이슈 목록은 월별 에피소드의 마지막 가용 상태다. 과거 지도 리포트 ID의 `~YYYY-MM-DD`는 그 날짜 상태를 고정한다. `issueKey`는 월이 바뀌어도 지도 위치를 유지하는 주제 키이고 `id`는 실제로 열 수 있는 리포트 키다. 지난 에피소드의 정규 ID에도 마지막 상태의 날짜를 보존한다.

`mock/client.js`는 보존된 source fixture를 실제 Spring의 8개 GET DTO로 투영한다. 일반 이슈 목록은 최신 스냅샷 36개를 페이지로 반환한다. 목록 468개를 한 번에 가져오지 않는다. 상세는 label/summary/members/relatedStocks(최대 5개 미리보기), 연관 종목은 별도 최대 100개, 종목 역연결은 최근 최대 50개다. 가격·시계열·뉴스·relatedEvents는 wire DTO에 추가하지 않고 UI에 미제공 상태를 표시한다. 기존 rich fixture의 합성 가격·뉴스는 역사 자료로 남지만 현재 화면에는 공급하지 않는다. `mock/identity.js`의 안정적인 숫자 매핑으로 지도/상세 ID를 맞추고 예전 slug 주소를 호환한다. 이 ID는 운영 DB ID가 아니다.

맵 인덱스는 375개 시점만 유지하고 실제 지도는 요청 시 하나씩 생성한다. 전체 지도 배열은 테스트/계약 검증용 `fixtures/pulse.js`에서만 생성하며 앱은 이를 가져오지 않는다. 날짜 선택과 슬라이더, 이전·다음, Home·End 키가 같은 전체 기간을 사용한다.

## 요청한 흐름과 현재 구현/명세의 차이

| 항목               | 확인한 차이와 이번 처리                                                                                                                                                                                                                                                                                        |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 리포트 → 종목 매칭 | 요구사항 §6.2는 완성된 LLM 리포트가 아니라 **클러스터 문서 제목·도입부 나열**을 임베딩 입력으로 사용한다. LLM 요약을 임베딩하는 방식은 품질·변동성 실험 후 채택하지 않았다. 화면의 리포트 → 종목 탐색 순서는 연결했지만 프로덕션 후보 생성 입력은 변경하지 않았다.                                             |
| 급증 탐지          | 제품 계약은 `사람 편집 1건 이상 → 조회수 급등`의 순차 관문이다(2026-09-17, WP-118). 현재 `spike/detector.py`는 아직 이전 OR 구현이므로 전환 전까지 명세와 코드가 다르다. DETECTED → VERIFYING → CONFIRMED는 조회수 2단계가 아니라 이후 AI 처리 상태다. 목데이터는 완성된 시연 상태이며 실제 판정과 별개다. |
| 자동 클러스터링    | 이번 주제 묶음은 수작업이다. 실 파이프라인의 급증 시간 동시성·기존 문서 재급증 포함 규칙과 Clickstream 수집을 실행한 결과가 아니다. `data-pipeline/streaming/edit_windows.py`의 집계와 별개다.                                                                                                                 |
| 과거 리포트 단절   | 이전 `historicalReport`는 최신 이슈를 복제하고 종목·뉴스·해석 배열을 비웠다. 이제 해당 날짜 클러스터에서 독립적으로 리포트와 종목 연결을 만든다.                                                                                                                                                               |
| 리포트 문서 그림   | `ArticleNetwork`의 방사형 선은 소속 표현이다. 실제 문서 쌍의 관계와 혼동하지 않도록 안내를 바꿨다. 펄스맵의 간선도 이번 데이터에서는 합성임을 표시한다.                                                                                                                                                        |
| 종목 범위          | 기존 목데이터에 NYSE·KRX가 섞여 있었다. 이번 프론트 목데이터는 Nasdaq-100으로 한정한다. 실 수집기 `data-pipeline/stock/universe.py`의 전체 미국 보통주 모집단을 변경한 것은 아니다.                                                                                                                            |
| API 연동           | 목데이터는 프론트 계약을 충족한다. 실제 백엔드 E2E 연결이나 실시간 처리 완료를 의미하지 않는다. 2026-09-15에 이전 event/entity 제안 계약을 현재 `/api/v1/issues`와 `/stocks`의 실제 DTO로 교체했다. 서비스·DB·파이프라인을 실행한 검증은 별도로 필요하다.                                                      |

제품에서 **리포트 본문을 읽고 종목을 매칭**하는 처리를 요구한다면 §6.2와 AI 입력 계약을 별도로 개정해야 한다. 이번 작업은 프론트 시연 흐름의 일관성을 확보하는 범위다.

## 출처와 갱신

- [Wikipedia Nasdaq-100 구성 목록](https://en.wikipedia.org/wiki/List_of_NASDAQ-100_companies): 구성 종목·사업 분류. 수집 시 리비전 ID를 저장한다.
- [Nasdaq 2026-06 정기 변경](https://ir.nasdaq.com/node/110541): ALAB·CRWV·NBIS·RKLB·TER 편입과 5종목 제외 확인.
- [Nasdaq Lumentum 편입 공지](https://ir.nasdaq.com/node/110416): LITE 편입 확인.
- [Nasdaq SpaceX 편입 공지](https://ir.nasdaq.com/news-releases/news-release-details/space-exploration-technologies-corporation-join-nasdaq-100): SPCX 편입 확인.
- [Nasdaq 공식 지수 화면](https://indexes.nasdaq.com/Index/Weighting/NDX): 전체 구성 데이터는 로그인 요구. Wikipedia 목록을 공식 구성 원장으로 주장하지 않는다.

갱신은 명시적으로 `python frontend/scripts/refresh-wiki-sources.py`를 실행한다. 표준 라이브러리와 Node.js만 필요하다. 공개 MediaWiki API의 리다이렉트를 정규화하고 누락/동음이의 문서를 거절한다. 최초 리비전은 API 제약 때문에 문서별로 조회하며 요청 제한을 존중해 재시도하고 OS 임시 폴더에 기준일별 캐시를 둔다. 실제 본문·편집 내역·조회수·시세는 수집하지 않는다. 기본 앱 실행과 테스트는 네트워크 없이 체크인한 파일을 사용한다.

갱신 기준일은 `history.js`와 갱신 스크립트의 날짜를 함께 변경해야 한다. 구성 종목 누락/추가는 시작 시 검증되며, 새 종목은 `topics.js`에 적절한 사업 맥락을 추가한다.

## 검증

`npm.cmd run test:data`와 `npm.cmd run test:contract`는 전체 날짜의 지도 형식, 참조 무결성, 클러스터/문서/리포트 수치 일치, 미래 데이터 혼입, 종목 모집단과 역연결을 검사한다. `npm.cmd run test:e2e`는 기간 경계 이동, 지도 → 과거 리포트 → 종목, 저장, 검색, 반응형 화면을 검사한다. `npm.cmd run test:api`는 가로챈 HTTP 응답을 사용한 계약 검증이다. 실제 Wikipedia 급증이나 라이브 서버의 통합 검증은 아니다.
