## 1. 대상 문서

v0.1 명세서 전문은 [requirements-v0.1.md](requirements-v0.1.md)에 있다. 같은 내용을 두 곳에 두면 한쪽만 갱신되어 어긋나므로 여기서는 반복하지 않는다.

요지: 위키피디아 편집 급증에서 실시간 이슈를 포착하고, 연관된 미국 상장 종목을 매칭해 이슈 피드로 제공한다. 실시간 경로는 EventStreams → Kafka → Spark Streaming → (급증 시) MapReduce로 검증·매핑·랭킹을 수행하고, 상세 페이지는 일단위 배치로 상관분석·유사 사례·유형 클러스터링을 계산한다. 필수 알고리즘 7종을 MapReduce(레이어 A)로 구현한 뒤 Spark(레이어 B)로 재구현해 성능을 비교한다.

## 2. 검토 결과 — 문서 내부 모순 3건

### M1. 이슈-종목 매핑 주체가 이중으로 지정됨 (중대)

**증상**

- 알고리즘 매핑표: Equi-Join이 "위키 아티클 - 기업/종목 매핑" 담당
- AI 활용 원칙: LLM이 "개념 -> 관련 종목" 추론 (PoC 완료)

같은 작업에 담당 컴포넌트가 둘로 적혀 있다.

**왜 문제인가 (1) — Equi-Join 단독으로는 성립하지 않는다**

Equi-Join은 키가 일치하는 행을 결합하는 연산이므로, 조인 키가 존재해야 한다. 여기서 쓸 수 있는 키는 Wikidata 속성이다.

| 속성 | 의미 |
| --- | --- |
| P249 | ticker symbol |
| P414 | stock exchange |
| P452 | industry |
| P17 | country |

급증 아티클 자체가 기업 문서인 경우에는 잘 동작한다.

```
아티클 "Nvidia" (Q182477) -> P249 = "NVDA", P414 = NASDAQ -> 조인 성공
```

그러나 실제로 편집 급증이 발생하는 문서는 대부분 기업 문서가 아니다.

```
"Strait of Hormuz"    -> 해협. P17=이란/오만/UAE. P249 없음
"Iran"                -> 국가. P249 없음
"2026 Taiwan tension" -> 사건. P249 없음
"Hurricane Milton"    -> 태풍. P249 없음
```

모두 P249가 NULL이므로 조인 결과는 0행이다.

반면 사용자가 기대하는 답은 명확히 존재한다.

```
Strait of Hormuz 봉쇄 위협
  -> 유가 급등     : XOM, CVX, OXY
  -> 유조선 운임 상승 : FRO, DHT, TNK
  -> 방산          : LMT, RTX
  -> 항공(악재)    : DAL, UAL   (연료비 상승)
```

이 연결은 Wikidata에 구조화된 관계로 존재하지 않는다. `Strait of Hormuz`와 `Frontline plc` 사이에는 관계 엣지가 없다. 이것은 인과·경제 지식이지 그래프 관계가 아니므로, Equi-Join이 원리적으로 수행할 수 없는 작업이다.

**왜 문제인가 (2) — Equi-Join이 MapReduce 잡으로서 정당화되지 않는다**

LLM이 매핑을 전담하고 Equi-Join이 "LLM이 반환한 회사명 5개를 티커 테이블에서 찾는" 역할만 한다면, 이는 5행 룩업에 불과하다. Redis 조회 몇 번이면 끝나는 작업이며, All-Pair Join이나 Repartition Join을 MapReduce로 구현할 근거가 사라진다. 필수 알고리즘 요구를 형식적으로만 충족한 상태가 되어 발표 시 방어가 어렵다.

### M2. 실시간 경로에 MapReduce가 포함됨

"급증 후보 발생 시 즉시 트리거 -> MapReduce 잡 실행"으로 되어 있으나, MR 잡은 기동 오버헤드만 수십 초이고 여기에 LLM + web_search가 붙으면 분 단위 지연이 발생한다. 이슈 피드 노출까지의 허용 지연을 명시해야 한다.

권고: MR 단계는 준실시간/배치로 포지셔닝하고, 피드에서는 "감지됨 -> 검증 중 -> 확정"의 단계적 상태를 노출하는 설계.

### M3. 역색인이 사용자에게 도달하는 지점이 없음

알고리즘 매핑표에는 역색인이 있으나, 주요 기능 목록에는 검색 UI가 없다(피드 중심 구성). 역색인 산출물의 소비처가 불명확하다.

권고: 검색 화면을 기능에 추가하거나, 역색인을 내부 매핑 보조 용도로만 한정해 명시.

## 3. M1 해결안 — 역할 재배치 (Join = recall, LLM = precision)

현재 문서는 `LLM 추론 -> Join으로 티커 결합` 순서로 읽힌다. 이 순서를 뒤집는 것을 제안한다.

```
1. 급증 클러스터 확정
     예: {Strait of Hormuz, Iran, Oil tanker, Petroleum}

2. 링크 이웃 확장 (아웃링크 + 백링크, 1~2 hop)
     -> 수천~수만 개 아티클 ID 집합

3. [Equi-Join / Repartition Join, MapReduce]
     좌: 이웃 아티클 집합 (수천~수만 행)
     우: Wikidata 상장기업 마스터 (P414 보유 전체, 수만 행)
     키: article_id (QID)
     -> 종목 후보 대량 생성 (recall 확보)
     -> 산업(P452)·국가(P17) 속성 동시 결합

4. 후보 스코어링
     링크 거리, 카테고리 중복도, 과거 동시급증 빈도 -> Top-N 압축

5. [LLM 검증·랭킹]
     "이 이슈에서 이 종목이 왜 관련 있는가? 방향(수혜/피해)은?"
     -> 근거 없는 후보 제거 (precision 확보)
     -> 사용자 노출용 설명 문장 생성

6. 티커 유니버스 대조
     -> 존재하지 않는 티커 제거 (LLM 환각 필터)
```

**역할 정리**

| 컴포넌트 | 역할 | 데이터 규모 |
| --- | --- | --- |
| Equi-Join (MR) | 후보 대량 생성 + 속성 결합 | 수만 × 수만 -> 분산 조인 정당화됨 |
| LLM | 인과 검증, 방향 판정, 설명 생성 | 후보 Top-N만 -> 비용 고정 |

기존 문서의 "LLM 비용은 이슈 후보 수에 비례하며 사용자 수와 무관하다"는 원칙은 그대로 유지된다.

**이 안의 약점**

3단계 링크 이웃 확장은 노이즈가 크다. `Iran` 문서의 아웃링크에는 `United States`, `Islam`, `Persian language` 등이 포함되고, 거기서 다시 무관한 기업으로 조인이 걸린다. 4단계 스코어링이 부실하면 후보군이 오염된다.

완화 수단:

- 링크 방향 가중 — 백링크가 아웃링크보다 신호가 강하다(기업 문서가 이슈 문서를 링크하면 실제 관련일 확률이 높음)
- hop 1로 우선 제한, 2-hop은 실험 후 결정
- 카테고리 교집합 필터 (`Category:Petroleum industry` 등)
- 급증 클러스터 전체 아티클과 공통으로 연결된 기업만 통과

이 스코어링 설계가 서비스 품질을 사실상 결정하므로, 감으로 튜닝하지 않기 위해 평가셋(Q21)이 필요하다.

**명세서 반영 문안**

알고리즘 매핑표의 Equi-Join 행을 다음으로 교체:

> **Equi-Join (All-Pair/Repartition)** — 급증 클러스터의 링크 이웃 아티클 집합 × Wikidata 상장기업 마스터를 조인하여 종목 후보군을 생성하고, 산업·거래소·국가 속성을 결합한다. (인과 판정은 수행하지 않으며, LLM 검증 단계가 담당한다.)

AI 활용 원칙에 다음 항목 추가:

> LLM은 Equi-Join이 생성한 후보군에 대한 검증·랭킹·설명 생성을 담당하며, 후보 생성 자체는 수행하지 않는다.

## 4. 미결 질문 (23건)

우선순위 최상위: **Q1, Q2, Q5, Q7, Q12** — 이 다섯 개가 나머지를 좌우한다.

### A. 이슈 정의

- **Q1.** "이슈" 1건의 단위는? 아티클 1개인가, 연관 아티클 클러스터인가? (피드 카드 하나에 대응되는 실체)
  - 권고: 클러스터. 아티클 단위면 `Iran`, `Iran–Israel`, `Strait of Hormuz`가 각각 카드로 분리되어 피드가 중복된다.
- **Q2.** 급증의 수학적 정의는? 윈도우 길이 / baseline 산출법 / 임계치.
  - 권고: 슬라이딩 윈도우 1h, baseline은 문서별 과거 28일 동시간대 EWMA, 임계 z-score 3 이상 **및** 최소 절대 편집수(예: 10) 동시 충족. 절대 하한이 없으면 평소 편집이 0건인 문서가 2건만 편집돼도 z값이 폭발한다.
- **Q3.** baseline용 과거 데이터 확보 방법은? 서비스 가동 후 28일을 쌓는 것은 일정상 불가능하다. Pageviews/Analytics API로 채울지, Dumps를 받을지, 짧은 baseline(72h)으로 타협할지.
- **Q4.** 수집 대상 언어는? 영문 위키만인지 전체 스트림인지. 전체면 초당 수십~수백 이벤트이므로 Kafka/HDFS 용량 계산이 달라진다.

### B. 매핑

- **Q5.** 비기업 아티클 -> 종목 경로를 무엇으로 확정할 것인가?
  - 후보: (a) LLM 추론 (b) 위키 링크 그래프 N-hop (c) Wikidata 관계 그래프 (d) 뉴스 텍스트 매개
  - 권고: 3장 해결안 채택 시 자동으로 "(b)+(c)로 후보 생성, (a)로 검증"이 된다.
- **Q6.** LLM 매핑 결과를 캐싱/재사용하는가? 동일 아티클이 반복 급증할 때 매번 호출하면 비용 원칙이 깨진다. 아티클-종목 매핑 테이블의 영속화 여부.
- **Q7.** 종목 유니버스 범위는? S&P 500 / 나스닥 전체 / 미장 전 종목(약 5,000)
  - 권고: S&P 500 + 나스닥100 합집합. 전 종목이면 yfinance 초기 적재와 상관계산 부담이 급증하고 매핑 정밀도도 떨어진다.

### C. 알고리즘 실체

- **Q8.** "벡터"가 두 종류로 혼재한다. 알고리즘표의 "벡터 유사도 셀프조인"은 시계열 패턴 벡터로 읽히고, 팀 역할표의 "벡터화/임베딩"은 텍스트 임베딩으로 읽힌다. 둘 다 사용하는지, KNN 입력이 어느 쪽인지 정의 필요.
- **Q9.** K-Means 이슈 유형 클러스터링의 입력 피처는? 텍스트 임베딩 / 위키 카테고리 원-핫 / 편집 패턴 통계. 또한 클러스터에 "정치·경제·산업" 레이블을 붙이는 주체는 누구인가(LLM인지 수동인지).
- **Q10.** 자카드 "과거 유사 이슈"의 집합 원소는? 관련 아티클 집합 / 매핑된 종목 집합 / 카테고리 집합.
- **Q11.** 상관분석의 시차(lag) 범위와 봉 단위는? 일봉이면 당일 급등을 포착하지 못할 수 있다. 이슈 발생 시점 전후 변동을 보여주려면 시간봉·분봉이 필요할 수 있으나, 무료 소스로 과거 분봉 확보는 어렵다(yfinance 분봉은 최근 60일 한정).

### D. 인프라

- **Q12.** 클러스터 하드웨어 스펙과 노드 수는? HDFS + MR + Spark + Kafka + HBase + Airflow + Spring + MySQL + Redis를 모두 올리면 메모리 요구가 크다. 제공 서버 사양과 대수 확인 필요.
- **Q13.** HBase가 실제로 필요한가? "대용량 시계열" 용도라 되어 있으나 종목 500개 × 일봉 5년 = 약 60만 행 수준이면 PostgreSQL로 충분하다. 위키 원본 이벤트 저장 용도라면 HDFS와 역할이 겹친다. 과제 요구인지 실제 필요인지 구분 필요.
- **Q14.** Kafka 보존 기간과 토픽 설계는? 전체 편집 스트림 상시 수집 시 디스크 계획이 필요하다.

### E. 데이터 소스

- **Q15.** yfinance 약관 검토 여부. 한국투자증권 API를 약관 사유로 제외했는데, yfinance는 Yahoo 공식 API가 아닌 비공식 스크래핑 래퍼다. 일관성 차원에서 판단 근거를 명세에 기록하는 편이 좋다.
- **Q16.** Alpha Vantage 무료 티어 한도 확인 필요. 최근 무료 플랜이 일 25요청 수준으로 축소된 것으로 알려져 있으며, 사실이라면 "보조/검증" 용도로도 사용이 어렵다. Finnhub(분당 60회) 등 대안 검토 여부.
- **Q17.** SEC EDGAR 재무제표는 어느 기능에서 사용하는가? 주요 기능 목록에 재무 관련 항목이 없다. 사용하지 않으면 데이터 소스에서 제외하고, 사용하면 기능에 추가한다.

### F. 서비스 기능 경계

- **Q18.** 관심종목은 회원 기능인데 인증 스펙이 없다. 로그인 방식(자체/OAuth)과 회원 정보 범위 결정 필요.
- **Q19.** "알림"의 전달 수단은? 웹 내 배지 / 브라우저 푸시 / 이메일. 구현 비용이 각각 다르다.
- **Q20.** 피드 정렬·보존 정책은? 최신순인지 급증 점수순인지, 이슈가 일정 기간 후 사라지는지 아카이브되는지.

### G. 검증·시연

- **Q21.** 품질 증명 방법은? 정답셋 없이 "이슈를 잘 잡는다"는 주장은 불가능하다. 과거 알려진 사건 N개로 재현 테스트하는 평가셋 구축 여부. (구축 시 발표에서 강력한 근거가 된다.)
- **Q22.** 레이어A(MR) vs 레이어B(Spark) 성능 비교의 측정 조건은? 동일 입력 크기·동일 클러스터·측정 지표(wall clock인지 처리량인지). 산출물이라면 명세에 고정하는 편이 안전하다.
- **Q23.** 시연 당일 급증 이슈가 발생하지 않으면? 위키 편집 급증은 통제 불가능하므로, 과거 사건 데이터를 재생하는 고정 시나리오 준비 여부.
