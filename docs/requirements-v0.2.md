# 요구사항 명세서 — WikiPulse (WikiPulse)

- 버전: **v0.2 (2026-09-17 개정)**
- 정본: 이 파일 (GitLab `docs/`). 개정은 MR로 한다. 노션은 읽기용 미러.
- 수치는 전부 실측이며 날짜를 붙였다 (11번).

---

## 1. 한 줄

위키피디아에서 **사람의 편집이 1건 이상 발생한 문서만 조회수 급등을 검사**하고, 조회수까지 급등한 문서를 묶어 **지금 뜨는 이슈 피드**를 만든다. 각 이슈에는 GDELT·벡터 검색으로 만든 미국 상장 종목 후보를 LLM으로 검증해 붙인다.

## 2. MVP 범위

**들어간다**

1. **이슈 감지·클러스터링** — 봇이 아닌 편집 1건 이상 확인 → 조회수 급등 확인 → 두 단계를 모두 통과한 문서를 이슈 단위로 묶음. 묶는 근거는 Wikipedia Clickstream과 사건 시점의 시간 신호
2. **버블맵** — 1번 결과의 시각화. 클러스터 = 버블, 크기 = 급등도. **시간 슬라이더로 과거 시점 재생(리플레이)**
3. **이슈 피드** — `/issues` 내부에서 카드/리스트 형식을 전환한다. 펄스맵(`/pulse`)은 독립 페이지이며 지도/목록 토글은 두지 않는다. (2026-09-09 정정, WP-37)
4. **이슈별 관련 미국 주식** — 후보 생성(벡터 유사도) → LLM 검증(근거 경로). 검증 통과분의 제품 노출 개수 상한은 두지 않기로 확정
5. **종목 상세** — 주가 그래프 + 이슈 발생 시점 표시 + 그 종목이 걸린 이슈 피드

**들어가지 않는다**

과거 유사 이슈 사례, 이슈 유형 자동 분류.

~~6. 회원 — 관심종목, 알림~~ · ~~7. 토론방 — 이슈별~~ → **서버·계정 기반 기능은 MVP 범위에서 제외 (2026-09-17, 팀원 1, WP-104).** MVP 조건 감사에서 발견 — 회원·관심종목·알림은 담당 Epic(WP-24)에 자식 스토리가 0개였고, 토론방은 애초에 담당 Epic 자체가 없었다(최초 Epic 12건 어디에도 없음). 남은 기간(GATEWAY 키 서비스별 사용 조건 확인, §10) 안에 핵심 루프(급증 감지→클러스터링→버블맵→이슈 피드→LLM 검증 종목 매칭→종목 상세)를 완성하는 게 우선이라 신규 착수하지 않기로 확정. WP-24는 backlog에 남기되 이번 프로젝트 기간엔 착수 안 함. 프론트에 남아 있는 브라우저 `localStorage` 보관함·토론은 다중 사용자 기능이 아닌 **UI 시연용 로컬 프로토타입**이며 MVP 완료 항목으로 세지 않는다.

### 3.1 컴포넌트별 역할 — 왜 있는가

| 컴포넌트 | 하는 일 | 없으면 |
| --- | --- | --- |
| **Kafka** | EventStreams(SSE)를 Spark가 읽을 수 있는 소스로 변환. 토픽 보존 기간 안에서 오프셋 되감기로 재처리 | Spark가 SSE를 직접 못 붙고, Spark 재시작 중 이벤트가 유실됨. 처리량은 이유가 아니다 — enwiki 초당 2건 |
| **Spark Structured Streaming** | 문서별 편집 이벤트를 받아 1건 이상 발생한 문서만 조회수 검사 대상으로 넘기고, 조회수 급등까지 통과한 문서를 클러스터링 | 스트리밍 자체가 안 됨 |
| **Spark 배치** | 28일 기준선 산출(수십억 행), GDELT 테마·지역 술어로 이슈 기사를 거른 뒤 관련 기관명과 lift 추출, 과거 원본을 LIVE와 같은 계약으로 재생해 클러스터 스냅샷 계산 | 단일 머신으로는 기준선·덤프 집계 불가 |
| **HDFS (2노드)** | 고정 MVP 구간(2026-07-17~09-17)의 편집·시간별 조회수·일별 user 조회수·GDELT·Clickstream 원본 보관. 두 EC2 디스크에 블록 분산, 복제 2 | 실제 공통 파이프라인 리플레이가 검증되기 전에 원본을 잃으면 재현·교정할 수 없음 |
| **PostgreSQL + pgvector** | 서비스 데이터 전부 — 이슈·클러스터(현재+스냅샷)·기준선·종목 마스터·주가. 종목 임베딩 벡터 저장과 코사인 Top-K. 회원·관심종목·알림·토론 테이블은 향후 기능용 스키마로만 남아 있으며 MVP에서는 사용하지 않음 | 별도 벡터 DB를 두면 종목 메타 조인이 두 번 왕복 |
| **LLM (Claude)** | 벡터 Top-K 후보 각각에 "왜 관련인가" 근거 경로를 생성할 수 있는지 판정. 통과분만 채택. 이슈 요약 문장 생성 | 임베딩 유사도만으로는 인과(호르무즈 → 유조선주)를 못 잡음 |
| **Spring Boot / React** | REST API, 버블맵·피드·종목 상세 UI | — |

### 3.2 처리 흐름

1. Producer가 EventStreams SSE를 읽어 `wiki.edits` 토픽에 넣는다. 대상은 `enwiki` namespace 0이며 봇 편집은 제외한다.
2. **1단계 — 편집 발생 확인.** 문서에 사람의 편집이 1건 이상 발생하면 조회수 검사 후보가 된다. 편집 z-score·편집 10건·편집자 2명 기준은 이 단계의 관문으로 사용하지 않는다. 이 단계만 통과한 문서는 아직 `spike`나 사용자 이슈로 확정하지 않는다.
3. **2단계 — 조회수 급등 확인.** 운영 최종 관문은 약 1시간 지연되는 Wikimedia `other/pageviews` **시간별 덤프**다. AQS 일별 API는 LIVE 최종 관문으로 사용하지 않으며, `pageview_complete` 일별 `agent=user` 덤프는 봇이 섞인 시간별 결과의 품질 검증용으로 함께 보존한다. 문서 생성 후 28일 이상 지났으면 직전 28일 조회수를 기준으로 `z ≥ 3 AND 평소의 2배 이상 AND 현재 조회수 100 이상`을 모두 적용한다. 생성 후 28일이 지나지 않았으면 **문서 생성 시각부터 현재 직전까지의 조회수**만 기준으로 사용하며, 28일이나 최소 7일이 찰 때까지 기다리지 않는다. 평균·표준편차를 계산할 표본이 없거나 기준 조회수가 0이면 `현재 조회수 ≥ 100`을 0에서의 유의미한 급등으로 본다. 조회수가 아직 도착하지 않았으면 1단계 후보로 보관했다가 도착 시 재판정한다. 조회수가 도착했지만 급등하지 않은 문서는 폐기하고, 통과한 문서만 `spike`로 저장한다. 목표는 사건 발생 후 통상 **1~2시간 이내 최종 노출**, 시간별 원본 도착 후 **내부 처리 15분 이내**이며 속도보다 정보 품질을 우선한다.
4. 통과 문서들을 **클러스터** = 이슈로 묶는다. 조회수 최종 관문을 직접 통과한 문서가 클러스터의 루트 씨드가 된다. 그 씨드의 Clickstream 이웃 중, 사건 시점과 생성 시각이 가까운 새 사건 문서는 추가 씨드(`is_seed=true`)로 묶고, 오래전에 생성됐지만 사건기간 편집이 다시 급증한 문서는 `재급증 비율 ≥ 5 AND 사건기간 편집 수 ≥ 20`일 때 비-seed(`is_seed=false`)로 묶는다. Clickstream 이동량은 포함 문턱이 아니라 `weight`로만 쓰며, Wikidata는 멤버 편입 관문으로 사용하지 않는다. 이미 포함된 멤버 사이의 Wikidata 관계를 화면 보조 간선으로 표시하는 것은 허용하지만 현재 소스 배선은 없다. 클러스터 `pulse_score`는 조회수 급등 강도를 중심으로 계산하며, 정확한 점수식 변경은 WP-118에서 구현·회귀 검증한다.
5. **여기부터(5~8)의 매칭·검증·요약은 Spring 워커가 맡는다** — 감지·클러스터링(2~4)은 Spark, 이후는 Spring으로 실행 경계가 갈린다. 워커는 클러스터 멤버 도입부로 대표 텍스트(§6.2)를 만들어 GATEWAY로 임베딩하고, pgvector에서 종목 임베딩과 코사인 Top-K(a)를 뽑는다. 여기에 GDELT lift 상위 Top-K(`cluster_org_mention`, b)를 합집합해 `BOTH`/`GDELT_ONLY`/`EMBEDDING_ONLY` tier와 함께 `cluster_stock`에 `verified=false`로 멱등 적재한다(임베딩 20 / GDELT 10). 이슈 임베딩은 후보 생성 시 계산해 쓰고 저장하지 않는다.
6. **(같은 Spring 워커 경계)** LLM이 Top-K 각각에 근거 경로(직접 언급 / 제품·산업 관계 / 공급망·고객·경쟁 / 지역 노출)를 생성할 수 있는지 판정한다. `cluster_org_mention`에 저장된 GDELT 기관명 상위를 컨텍스트로 준다(RAG). GDELT 테마·지역은 이슈 기사를 고르는 검색 술어로만 쓰며 현재 저장하거나 LLM에 직접 전달하지 않는다. 통과한 것을 tier 우선(§6.3: BOTH → GDELT_ONLY → EMBEDDING_ONLY)으로 낸다. 이 단계가 `cluster_stock`의 `verified`·`match_path`·`rationale`을 채운다.
7. 대표 텍스트와 GDELT 컨텍스트를 근거로 **사용자용 한국어 이슈 요약**을 생성해 `issue_report`에 멱등 저장한다. 이 요약은 화면용이며, §6.2의 임베딩 입력을 대체하지 않는다.
8. 이슈 요약 + 검증된 종목 + 종목별 연결 근거를 PostgreSQL에 쓰고 API가 낸다. 버블 점수·멤버는 시점별 `cluster_snapshot` 결과이고, 요약·검증 종목은 `issue_key` 단위 결과를 재사용한다. 과거 시점을 선택하면 **그 시점까지 생성 완료된** 요약·종목만 보여야 하며, 같은 `issue_key`라는 이유로 미래 결과를 소급 노출하지 않는다. 피드 상태 **감지됨 → 검증 중 → 확정**은 조회수 2단계가 아니라, 이슈 확정 후 매칭·요약 진행 상태를 뜻한다.
9. **리플레이와 LIVE의 계약은 하나다.** 고정 과거 구간은 **2026-07-17~2026-09-17**이고, 이후에는 LIVE 원본과 최신 스냅샷을 계속 누적한다. 과거의 편집·시간별 조회수·일별 user 조회수·GDELT·Clickstream 원본을 HDFS에 올려 LIVE와 같은 정규화·감지·클러스터링·요약·종목 매칭 계약으로 미리 계산한 `cluster_snapshot`을 저장한다. LIVE는 같은 계약의 최신 스냅샷이다. 실제 공통 파이프라인 재생 결과를 검증하기 전에는 MVP 구간 원본을 폐기하지 않는다.
10. **종목 상세**: yfinance 일봉을 PostgreSQL에 적재. 그래프 위에 그 종목이 걸린 이슈의 발생 시점을 표시하고, 아래에 해당 이슈 피드를 붙인다.
11. **장애와 정상 0건을 구분한다.** 조회수 원본 미도착은 후보 대기, GATEWAY·GDELT 실패는 재시도 또는 처리 중 상태다. 요약·후보 생성·종목 검증이 모두 끝났는데 통과 종목이 없을 때만 정상적인 관련 종목 0건으로 확정한다. 실패나 미도착을 빈 정상 결과로 저장·노출하지 않는다.

> **구현 상태 점검(2026-09-17):** 5번 후보 생성(WP-67)과 6번 종목별 LLM 검증(WP-68)은 코드가 있다. 7번 실시간 요약 생성·`issue_report` 적재와 `DETECTED → VERIFYING → CONFIRMED` 상태 전이는 데모 시드 외 실행 코드가 없어 WP-119로 등록했다. 로컬 DB에는 종목 임베딩 0건·GDELT 기관 언급 0건이고 Docker backend에 워커 설정도 전달되지 않는다. 또한 클러스터에서 GKG 검색 술어를 만드는 규칙과 GKG 집계 자동 실행 배선도 없어, 5~6번 E2E 검증은 WP-120으로 등록했다. 감지 2단계의 현재 코드는 아직 OR 방식이며 LIVE 경로는 조회수를 넣지 않으므로, WP-118 구현 전까지 명세와 코드가 다르다. 클러스터 코드도 추가 씨드를 전부 `is_seed=false`로 저장하고 비-seed 재급증 규칙을 구현하지 않아 위 4번 계약과 다르다.
>
> **로컬 시드 주의:** 2026-07-17~09-17 시드는 1,112개 `issue_cluster`를 전부 `CONFIRMED`로 고정하지만 `issue_report`는 이슈별 마지막 스냅샷 18건에만, `cluster_stock`은 마지막 이란 이슈 스냅샷 1건에 3종목만 붙인다. API·화면 시연용 수작업 데이터이며 실제 공통 파이프라인 결과가 아니다. 최종 MVP 완료 조건은 고정 구간의 실제 원본을 위 공통 계약으로 재생한 결과로 시드를 교체하고, 과거 스냅샷과 이후 LIVE 누적을 함께 검증하는 것이다.

### 5.1 문서 제목 canonical 규칙 (2026-09-13 확정, WP-79)

`wiki_page`의 자연키가 `(wiki, title)`이라, 같은 문서가 경로마다 다른 제목 표기로 들어오면 한 문서가 두 행으로 갈라진다. **파이프라인 내부 canonical은 공백형이다** — `Hurricane Milton`.

| 경로 | 원래 표기 | 처리 |
| --- | --- | --- |
| LIVE EventStreams | 공백형 | 그대로 (계약 고정용으로 함수는 통과시킨다) |
| `mediawiki_history` 덤프 | 밑줄형 | `canonical_title`로 변환 (`batch/normalize_dump.py:normalize_dump`) |
| `pageview_complete` 덤프 | 밑줄형 | ~~-57 머지 후 적용~~ → **적용됨** (`batch/pageview.py:parse_row`, 2026-09-15) |
| Clickstream 덤프 | 밑줄형 | 자체 변환(`raw.replace("_", " ")`). 공통 함수 통합은 후속 — 아래 ⚠️ |

구현은 `data-pipeline/producer/normalize.py`의 `canonical_title()` **한 곳**이다. 경로마다 따로 구현하지 않는다. 위 표의 앞 세 경로가 이 함수를 import해 쓴다.

⚠️ **Clickstream만 아직 자체 구현이고, 결과가 완전히 같지는 않다.** `batch/clickstream.py:canonical_title`은 `replace("_", " ")`뿐이라 **연속 축약·trim이 없다.** `Hurricane__Milton`이 공통 함수로는 `Hurricane Milton`, 여기서는 `Hurricane  Milton`(공백 2개)이 되어 같은 문서가 `(wiki, title)` 두 행으로 갈라진다. Clickstream은 WP-79의 AC가 아니라 손대지 않았다 — 후속으로 통합한다.

**적용 시점 규칙 (⚠️ 조용히 틀리는 지점)**: canonical은 **namespace/유효성 필터 뒤, 집계 키가 되기 전**에 건다.

- 앞으로 당기면 — `pageview.py`의 namespace prefix 목록이 `User_talk`처럼 밑줄형이라 `User talk`와 일치하지 않는다. namespace 문서가 ns0로 새어 들어온다.
- 뒤로 미루면 — 이미 원래 표기로 그룹이 갈린 뒤라 `Hurricane_Milton`과 `Hurricane__Milton`이 별개 키로 집계된다. 출력 직전 문자열 치환은 이 문제를 못 고친다.

회귀 테스트: `batch/tests/test_pageview.py`의 `test_표기만_다른_같은_문서가_한_키로_합산된다`(집계 전 적용 확인)·`test_canonical_이_namespace_필터보다_뒤에_걸린다`(순서 확인).

**공백형을 고른 이유**

1. MediaWiki가 밑줄로 주든 공백으로 주든 **공백형으로 정규화해 돌려준다**. 밑줄은 URL 표기이지 제목이 아니다.
2. `edit_event` 계약(`data-pipeline/README.md`)·API 명세(`docs/api-v0.2.md`)·DB 테스트가 **이미 전부 공백형**이다. 밑줄을 고르면 확정된 API 계약을 깨야 한다.
3. 밑줄을 내는 곳이 `batch/normalize_dump.py` 하나뿐이라 바꿀 곳이 제일 적다.
4. 공백형이 곧 MediaWiki의 표시 제목이라 **표시용 컬럼을 따로 둘 필요가 없다** (아래).

**적용하는 규칙** (2026-09-13 MediaWiki API `normalized` 응답 실측)

| 규칙 | 예 |
| --- | --- |
| 밑줄 → 공백 | `Hurricane_Milton` → `Hurricane Milton` |
| 연속 구분자 → 공백 하나 | `Hurricane__Milton` → `Hurricane Milton` |
| 앞뒤 구분자 제거 | `_Hurricane Milton_` → `Hurricane Milton` |

뒤 둘은 방어용이다. LIVE 표본 2,496건에 연속 공백이 0건이라 실제로는 값이 바뀌지 않는 게 정상이다.

🔴 **적용하지 않는 규칙 — 추측으로 넣지 말 것**

- **첫 글자 대문자.** 소스가 주는 건 이미 대문자화된 MediaWiki 저장 제목이다 — `eBay`를 조회하면 저장 제목이 `EBay`(pageid 130495)다. 우리는 사용자가 친 제목을 받지 않는다. 게다가 이 규칙은 위키별 `$wgCapitalLinks` 설정에 달렸고 **enwiki 밖에서는 확인하지 않았다**.
- **Unicode NFC.** MediaWiki가 NFC로 저장·요구하고(API가 비-NFC 입력에 경고를 낸다), LIVE 표본 2,496건이 전부 NFC였다. 소스가 이미 NFC라 no-op이다.

⚠️ **NFC·연속 밑줄 여부를 덤프 쪽(`mediawiki_history`·`clickstream`·`pageview_complete`)에서는 확인하지 못했다.** 로컬에 덤프가 없고 HDFS 접근이 막힌 상태에서 판단했다. "같은 MediaWiki가 만든 제목"이라는 추론이며 실측이 아니다. 덤프 표본이 생기면 재확인한다.

**표시용 title은 분리하지 않는다.** 공백형이 곧 MediaWiki의 표시 제목이라(`Hurricane Milton`·`EBay`) 내부 식별용과 표시용이 같은 문자열이다. 나누면 두 값이 갈라질 위험만 생긴다. `wiki_page.title` 한 컬럼을 그대로 쓴다.

**기존 HDFS 산출물 재생성 — 필요하지만 이 스토리 범위 밖**

`/wikipulse/raw/mediawiki_history/`(WP-56, enwiki 2025-06·2024-10)에 쌓인 JSONL은 `normalize_dump.py` 출력이라 **밑줄 제목을 담고 있다.** 원본이 아니라 내부 계약(`edit_event`) 산출물이므로 canonical이어야 맞다 → **논리적으로 재생성 대상**이다.

- 다만 **지금 틀린 결과를 내고 있지는 않다.** 소비자인 `cluster/driver.py:load_creation_dates`가 아직 `NotImplementedError`라 이 파일들을 읽는 코드가 없다.
- 비용: 덤프 재다운로드 1.1 GB + 변환 771s·477s + 재적재.
- 🔴 **읽을 때 canonical을 적용하는 우회안은 영구 해법으로 쓰지 않는다.** HDFS에 두 가지 제목 표기가 공존하게 되는데, 그게 정확히 이 규칙이 없애려는 실패 모드다.
- `pageview_complete`(WP-57) 산출물도 같은 문제·같은 결론이다. **두 개를 한 후속 이슈로 묶는다.**

### 6.2 이슈 대표 텍스트 (2026-09-08 확정)

클러스터는 문서 여러 개인데 임베딩·LLM 입력은 글 한 덩이여야 한다. 그 변환 규칙:

```
{문서 제목}: {도입부 앞 N문장}
{문서 제목}: {도입부 앞 N문장}
...
```

- N = 클러스터 문서가 1개면 6, 2~3개면 4, 4개 이상이면 2. 전체 상한 2,000자
- 문서 순서는 급등도(`pulse_score`) 내림차순
- 출처는 Wikipedia API `prop=extracts&exintro&explaintext`, 리다이렉트를 따라간다
- 🔴 **텍스트는 영어로 유지한다.** 종목 설명이 영어라 이슈 텍스트를 한국어로 만들면 언어 불일치만으로 코사인이 절반이 된다 (정답 평균 0.160 → 0.081, 11번). 사용자에게 보여줄 한국어 요약은 후보 검증과 별도로 3.2 7번에서 만든다.

~~LLM 한 번 호출해 이슈를 요약한 뒤 그것을 임베딩~~ → **채택하지 않는다** (2026-09-08). 랭킹 품질이 나열 방식과 동률인데 호출 1회와 4~6초가 붙고, 조용히 틀리는 실패 모드 셋이 실측됐다: ① 프롬프트 언어를 따라가 한국어 요약이 나오면 코사인 반토막 ② 정보가 부족하면 "설명할 수 없다"는 거부 문장이 그대로 임베딩됨 ③ 입력에 없는 사건을 지어냄 ④ 같은 입력으로 4회 돌렸을 때 나열 방식은 값이 동일한데 LLM 요약만 정답 평균순위가 3.3~7.0으로 흔들렸다 — 파라미터 튜닝 효과가 잡음에 묻힌다. 근거는 `ai/issue-text-poc/RESULT.md`.

### 6.3 후보 생성과 검증

- **후보 (recall)** — 두 경로의 합집합:
  - (a) 이슈 임베딩 ↔ 종목 임베딩 코사인 **Top-20**. pgvector 한 쿼리. 설명서에 그 리스크가 적힌 종목을 잡는다 (보험사, 에너지 인프라)
  - (b) GDELT 동시 출현 lift 상위 **Top-10**. 이슈 기간 기사에서 기관명을 뽑아 종목 마스터와 조인. 설명엔 없는 2차 효과를 잡는다 (플로리다 전력, 발전기, 항공 결항)
  - 둘의 교집합은 작다 — Milton K=10에서 1개, K=30에서 3개 (11번). 합집합이 맞다. 다만 **(b)가 주력이고 (a)는 보충**이다: 사건 서술과 사업 설명은 같은 종류의 텍스트가 아니라 임베딩 코사인이 0.2 안팎으로 낮고, 정답(NEE·Lennar·Generac)과 노이즈(Monster Beverage·Intel)가 섞여 나온다. (a)의 몫은 기사에 아직 이름이 안 나온 첫 시간대와 기업 문서 이슈다
- **우선순위 — 교집합 먼저**:
  1. **(a) ∩ (b)** — 두 신호가 일치. 먼저 검증하고 통과하면 최상단. Milton K=10 교집합 NEE, K=30 NEE·Generac·Exxon — K가 커지면 노이즈도 들어오므로 LLM 면제는 아니다
  2. **(b) − (a)** — GDELT 단독. 정답 밀도가 높다
  3. **(a) − (b)** — 임베딩 단독. **1·2등급 통과(LLM 검증 확정)가 2개 미만일 때만** 검증한다. 임베딩 노이즈(Monster Beverage·Intel)가 대부분 여기 있어서 LLM까지 안 간다
- **검증 (precision)**: LLM이 후보마다 근거 경로를 만들 수 있는지 판정. 못 만들면 버린다. 고정 유사도 컷은 두지 않는다. **노출 개수 상한도 두지 않는다** — LLM 검증을 통과한 것만 화면에 나가므로 이미 자연 상한이 걸려 있고, 정답셋 최댓값(Milton 9개)도 스크롤 범위 안이다.
- **컨텍스트 (RAG)**: (b)에서 나온 기관명 상위를 LLM에 준다. 뉴스 동시 출현이 인과 경로의 근거가 된다. GDELT 테마·지역은 이슈 기사 필터 술어이며 현재 `cluster_org_mention`에 저장하지 않아 LLM 입력에는 포함되지 않는다.
