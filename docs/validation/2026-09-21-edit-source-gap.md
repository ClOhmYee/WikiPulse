## 1. 공백이 정확히 어디서 시작하나

`--probe dump` · `--probe cadence`

`mediawiki_history` 는 스냅샷 단위로 나오고 **마지막 달 파일이 잘려 있다.** 이건
추측이 아니라 두 스냅샷에서 같은 형태로 관측된다.

| 스냅샷 | 공개일 | 직전 달 | 마지막 달 | 마지막/직전 |
| --- | --- | --- | --- | --- |
| 2026-07 | 07-Aug-2026 | 2026-07 = 547,673,972 B | 2026-08 = 1,986,312 B | 0.36% |
| 2026-08 | 02-Sep-2026 | 2026-08 = 569,877,751 B | 2026-09 = 3,145,030 B | 0.55% |

2026-09 스냅샷은 **아직 없다** (`/other/mediawiki_history/` 에 `2026-07`·`2026-08`
둘뿐). 공개 간격이 한 달이고 각각 다음 달 **2일·7일**에 나왔으므로 2026-09 스냅샷은
**2026-10-02~07 경**으로 본다.

잘린 `2026-08.enwiki.2026-09.tsv.bz2` 를 실제로 받아 열어 보니:

```
revision 행 34,792 / event_entity 분포 {page: 2,543, revision: 34,792, user: 1,459}
revision 최대 시각 2026-09-01 02:29:37.0
```

⚠️ **"09-01 하루치" 가 아니라 두 시간 반이다.** https://github.com/ClOhmYee/WikiPulse 에 하루치로 적혀 있는데
실제로는 `2026-09-01 00:00:00 ~ 02:29:37` UTC 다.

⚠️ **마지막 분이 분 중간에서 잘렸다.** 분당 분포가 `02:26 196 · 02:27 192 ·
02:28 167 · 02:29 110` 이다. 마지막 분을 통째로 믿으면 편집 수가 조용히 모자란다 —
**02:29 는 버리고 02:00 까지를 덤프 경계로 쓴다.**

**공백 = 2026-09-01 02:00 ~ 2026-09-17 24:00 UTC, 약 17.0일.**

시간별 조회수 raw 는 이 구간도 EC2 에 이미 있다 (WP-155, 2,184시간·gap 0).
없는 것은 편집 쪽뿐이고, 편집이 없으면 candidate title 을 못 만들어 조회수를 걸러낼
기준이 사라진다.

일 단위로 좁힌 뒤 분 단위까지 이분 탐색했다.

```
-200일 미보존 · -100일 미보존 · -50일 미보존 · -25일 보존
-37일 미보존 · -31일 미보존 · -28일 보존 · -29일 보존 · -30일 보존
→ 분 단위: 2026-08-22 02:17Z 경계
가장 오래된 조회 가능 행 2026-08-22 02:27:53Z
보존 폭 약 29일 23시간
```

🔴 **슬라이딩이라는 것도 실측됐다.** 같은 탐색을 15분 간격으로 두 번 돌렸더니 가장
오래된 행이 `02:17:04` → `02:27:53` 로 **10분 49초 밀렸다.** 고정 구간이 아니라
매 순간 뒤에서 잘려 나간다.

⚠️ **보존 밖을 요청해도 빈 배열이 아니다.** API 는 "없음" 대신 **가장 오래된 행**을
돌려준다. 그래서 개수로 판정하면 미보존 구간이 "데이터 있음"으로 보인다. 스크립트는
요청 시각과 실제 첫 행의 **시차**로 판정한다 (`RETAINED_SLACK_SEC = 600`).

⚠️ **표본을 성기게 찍으면 못 찾는다.** `-25일 보존` 과 `-50일 미보존` 두 점만 봤다면
경계를 "한 달 어딘가"로 적고 끝났을 것이다. GDELT 결손 구간에서 이미 한 번 물린
형태다 (https://github.com/ClOhmYee/WikiPulse 작업 원칙).

## 3. 덤프 대비 일치율 — 겹치는 1시간 전수 비교

`--probe compare`, 구간 2026-09-01 01:00~02:00 UTC (덤프와 API 가 둘 다 가진 유일한 창)

덤프 쪽 정답은 손으로 다시 짜지 않고 저장소의 `batch.schema.field` +
`producer.normalize.canonical_title` 를 그대로 썼다. 계약이 갈리면 비교가 무의미하다.

```
덤프: revision ns0 11,635행 (봇 5,331 = 45.8%) / 제목 9,537 / 비봇 제목 4,228
RC:   11,494행        (봇 5,321 = 46.3%) / 제목 9,448 / 비봇 제목 4,140 / 호출 23
ARV:  11,647행                           / 제목 9,556          / 호출 31 (봇 플래그 없음)
```

| 비교 | 재현율 | 정밀도 | 자카드 |
| --- | --- | --- | --- |
| **RC 비봇 vs 덤프 비봇** | **0.9787** | **0.9995** | **0.9783** |
| RC 전체 vs 덤프 전체 | 0.9904 | 0.9997 | 0.9900 |
| `allrevisions` 전체 vs 덤프 전체 | 0.9964 | 0.9945 | 0.9909 |
| `allrevisions` 전체 vs 덤프 **비봇** | 0.9931 | **0.4394** | 0.4381 |

재현율 = 덤프 제목 중 API 가 가진 비율, 정밀도 = API 제목 중 덤프에 있는 비율.

### `allrevisions` 를 쓰지 않는 이유

`list=allrevisions` 는 revision 테이블을 직접 읽어 **보존 제한이 없다.** 그래서 처음엔
이쪽이 답으로 보였다. 하지만 `arvprop` 에 **봇 플래그가 없다.**

이 구간 편집의 **45.8% 가 봇**이라, 봇을 못 거르면 candidate title 의 정밀도가
**0.4394** 로 떨어진다. 이슈 판정 1차 관문이 "봇이 아닌 편집 1건 이상"(명세 §3.2)인데
그 관문이 통째로 무력해진다. 봇 여부를 `list=users&usprop=groups` 로 사후 조회하는
길은 있지만, 봇 그룹에 없는 봇·과거 시점 그룹 변경이 또 다른 오차원이 된다.

**RecentChanges 는 `rcprop=flags` 로 봇 플래그를 그대로 준다.** 봇 비율도 덤프
45.8% vs RC 46.3% 으로 맞는다.

### 2.1% 차이의 원인 — 문서 이동이다

RC 비봇에 없고 덤프 비봇에만 있던 제목 90개를 전수 조회했다.

| 분류 | 개수 | 예 |
| --- | --- | --- |
| 지금도 같은 제목으로 존재 | 53 | `Henry I of Burgundy`, `Frederick I of Lorraine` |
| 리다이렉트로 이동됨 | 50 | `Charles II, Duke of Lorraine`, `Francis I, Duke of Lorraine` |
| 없음 (삭제 또는 이동) | 13 | `Genc Nimoni`, `C-nario` |

(분류가 겹친다 — 리다이렉트를 따라가면 존재하는 문서로 붙는다.)

압도적으로 **대량 문서 이동 작업**이다. 이름이 줄줄이 `... of Lorraine` /
`..., Duke of Lorraine` 으로 짝을 이룬다. `allrevisions` 쪽 차이도 같은 성격이다 —
`Battle of Gabés` ↔ `Battle of Gabès`, `2026 Nepal floods` ↔ `2026 Nepal–Tibet floods`.

🔴 **덤프는 `page_title_historical`(사건 당시 제목), API 는 현재 제목을 준다.**
`normalize_dump` docstring 이 `_historical` 변종을 써야 한다고 이미 경고한 축과 같다.
따라서 RC 로 채운 구간은 **제목 기준이 미세하게 다르다.** 2.1% 규모이고 대부분
이슈성이 낮은 문서(중세 로렌 공작 목록 정리)지만, 이 구간만 성격이 다르다는 것을
알고 쓴다.

### 비용

RC 는 **시간당 23호출 · 하루 552호출**이다. 공백 17.0일이면 **약 9,400호출**,
0.2초 간격이면 순수 대기만 **약 32분**, 429 재시도를 얹어 **1~2시간**으로 본다.

⚠️ **429 를 실제로 맞았다.** 연속 호출이 몇 백 건을 넘기자 `HTTP Error 429` 가
났고 `Retry-After: 43~46` 이 왔다. 스크립트에 지수 백오프를 넣어 해결했다. 9,400호출
짜리 수집을 재시도 없이 돌리면 중간에 죽는다.

## 4. 결론과 권고

**"대안 구현"을 택한다. 단 지금 한다.**

1. 🔴 **2026-10-01 이전에 RC 원본을 받아 둔다.** 공백 17.0일 × 552호출/일 ≈ 9,400호출,
   1~2시간. 받아 두면 덤프가 밀리든 말든 복구 가능하다. 안 받아 두고 덤프가 하루라도
   밀리면 09-01~09-02 는 영구 손실이다. 원본은 candidate title 로 가공하기 전 **raw
   그대로** 보존한다.
2. 2026-10-02~07 에 2026-09 스냅샷이 나오면 **덤프를 정본으로 갈아끼운다.** RC 는
   그때까지의 보험이자, 갈아끼운 뒤에는 같은 구간을 두 소스로 대조한 증거가 된다.
3. MVP 노출 구간 `2026-07-17~09-17` 은 **축소하지 않는다.** 지금 줄이면 되돌릴 근거를
   버리는 셈이고, 위 1·2 중 하나만 되어도 구간이 채워진다.

### 구현 시 지킬 것

- 봇 판정은 **RC 의 `bot` 플래그**를 쓴다. `allrevisions` + 사용자 그룹 조회로 대체하지
  않는다 (§3 정밀도 0.4394).
- 덤프 경계는 **2026-09-01 02:00Z**. 잘린 마지막 분(02:29)은 버린다.
- 제목은 `producer.normalize.canonical_title` 을 그대로 통과시킨다. RC 는 공백형으로
  오지만 `canonical_title` 은 멱등이다.
- 429 백오프 필수.
- RC 로 채운 구간은 **제목이 현재 기준**이라는 것을 산출물 manifest 에 적는다.

### 이 검증이 하지 않은 것

- 공백 **전 구간**을 실제로 받아 보지 않았다. 일치율은 **겹치는 1시간 전수 비교**이고,
  다른 시간대·요일에서 같은 수치가 나온다는 보장은 없다. 특히 봇 비율(45.8%)은 시간대
  의존이 크다.
- ~~RC 가 **삭제된 문서의 편집**을 어떻게 다루는지 따로 재지 않았다.~~ → **쟀다**
  (2026-09-22, WP-184). 아래 절.
- 2026-09 스냅샷 공개일은 **두 회차(07-Aug·02-Sep)에서 외삽한 값**이다. 위키미디어

## 후속 실측 — 이동·삭제 보충 (2026-09-22, WP-184)

전 구간 수집(406/406 · 1,965,182행)을 끝내고 `rctype=log` 도 같은 구간으로 받았다
(48,954행 · 408호출 · 40분). 이음매 구간에서 덤프와 다시 맞댔다.

재현: `python -m batch.rc_candidates --verify-seam <덤프> --log-root <log 수집본>`

### 무엇이 빠졌던가 — 이동과 보호

`rctype=edit|new` 로는 **문서 이동**이 만드는 revision 을 못 받는다. 이동 하나가
revision 두 개(원본에 남는 리다이렉트 + 대상 문서)를 만드는데 RC 는 그것을 `log` 로
준다. **보호(protect)도 null revision 을 만든다** — 이건 예상 못 했다가 대조에서 나왔다.

| 이음매 `2026-09-01 02:00~02:29Z` | 값 |
| --- | ---: |
| 덤프 revision | 3,660 |
| RC `edit\|new` revision | 3,627 |
| **RC 에만** (중복) | **0** |
| 덤프에만 (누락) | 33 |
| └ `log` 의 revid 로 회수 — move | 13 |
| └ `log` 의 revid 로 회수 — protect | 2 |
| └ 잔여 | 18 |

### 🔴 revid 로 맞추면 절반을 놓친다 — 제목으로 맞춘다

로그는 이동이 만든 revision 두 개 중 **revid 를 하나만** 준다. 그래서 revid 기준
잔여가 18건인데, 그중 **14건은 로그의 `title`·`logparams.target_title` 로 커버**된다.

이 산출물이 내는 것은 **candidate title** 이지 revision 목록이 아니다. 필요한 것이
애초에 제목이므로 제목으로 맞추는 것이 맞다.

| 제목 기준 | 값 |
| --- | ---: |
| 덤프 고유 제목 | 3,055 |
| RC `edit\|new` 만 | 3,037 (99.41%) |
| **RC + log** | **3,051 (99.87%)** |
| 누락 | **4** |

### 남은 4건은 전부 삭제된 문서다

| 제목 | 편집 | 삭제 |
| --- | --- | --- |
| `Eleanor Sillerico` | 02:0x | 09-01 13:17 |
| `Maria Nosulia` | 02:0x | 09-07 01:33 |
| `Blight (race)` | 02:0x | 09-08 18:39 |
| `Ellen Imelda Cashman` | 02:01:14 생성 | 09-02 01:00 삭제 → 09-02 07:20 **재생성** |

편집은 있었는데 그 뒤 문서가 지워지면서 RC 의 `edit|new` 항목이 사라졌다. `log` 의
`delete` 로는 **삭제 사실만** 알 수 있고 그 이전 편집은 되살리지 못한다.

⚠️ **이것을 누락으로 셀지는 별개 판단이다.** 삭제된 문서는 이슈가 될 수 없으므로,
candidate title 로서는 빠지는 것이 오히려 맞을 수 있다. 전 구간 `delete` 로그가
7,759건이라 규모는 작지 않다.

⚠️ 위 수치는 **이음매 30분 구간 하나**다. 다른 시간대에서 같은 비율이 나온다는 보장은

### 정정

이 문서 §3 의 "2.1% 차이가 거의 전부 대량 문서 이동"은 방향이 맞았다. 다만 그때는
기록만 하고 넘어갔는데, 실제로 `rctype=log` 로 **회수 가능**하다는 것이 확인됐다.
