# GATEWAY 프롬프트 캐싱 — 적용 시도와 폐기

- 검증 ID: `VAL-2026-09-20-GATEWAY-01`
- 실행일: 2026-09-20 KST
- 환경: 서비스 EC2 에서 GATEWAY 게이트웨이 직접 호출
- 대상: WP-150
- 판정: **폐기 — 켜면 25% 더 비싸다**

## 1. 왜 시도했나

`LlmVerifier` 는 **후보 하나당 1회** LLM 을 부른다("후보 하나를 LLM 으로 검증한다", 그쪽 docstring).
한 클러스터의 후보 20~25개가 전부 같은 컨텍스트를 새로 싣는다.

2026-09-20 운영 실측 (`Air India Flight 171`, 후보 25개):

| 구성 | 크기 | 후보마다 바뀌나 |
| --- | --- | --- |
| 시스템 프롬프트 | 4,773자 | ❌ |
| 이슈 대표 텍스트 | 695자 | ❌ |
| GDELT 기관 컨텍스트 | 436자 | ❌ |
| 지시문 | ~200자 | ❌ |
| 종목 사업설명 | 평균 1,084자 | ✅ |

**요청의 84%가 후보마다 동일하다.** 캐시 적중분은 입력 단가의 1/10 이므로 큰 절감이 기대됐다.

## 2. 결과 — 쓰기만 되고 읽기가 안 된다

같은 요청을 GATEWAY 에 **4회 연속** 보냈다.

```
cached 1: in=8    write=1143  read=0
cached 2: in=8    write=1143  read=0
cached 3: in=8    write=1143  read=0
cached 4: in=8    write=1143  read=0
plain   : in=1151 write=0     read=0     ← cache_control 없는 기준선
```

🔴 **네 번 다 캐시 쓰기다.** 캐시 쓰기는 입력 단가의 **1.25배**이므로:

```
캐시 없음 : 1,151 × 1.00 = 1,151
캐시 적용 :     8 × 1.00 + 1,143 × 1.25 = 1,437     ← 25% 증가
```

절감이 아니라 **순증**이다.

## 3. 원인 (추정)

`cache_control` **자체는 게이트웨이를 통과한다** — `cache_creation_input_tokens` 가 차는 것이 증거다.
그런데 읽기가 안 붙는다.

가장 그럴듯한 설명은 **GATEWAY 가 상위 계정을 다중화**하는 것이다. Anthropic 프롬프트 캐시는
**조직 단위**라, 요청마다 다른 상위로 나가면 앞 호출이 만든 캐시가 보이지 않는다.

⚠️ 게이트웨이 내부는 확인할 수 없으므로 이건 **추정**이다. 확실한 것은 관측된 사실뿐이다 —
쓰기는 되고 읽기는 0 이다.

## 4. 🔴 이게 조용히 틀리는 방식

- API 가 **400 을 주지 않는다.** 요청은 정상 처리된다.
- `cache_creation_input_tokens` 가 **차오른다.** 로그만 보면 캐싱이 동작하는 것처럼 보인다.
- `cache_read_input_tokens` 를 **같이 보지 않으면** 비용이 늘어난 줄 모른다.

즉 "적용했다"고 믿고 넘어가기 쉬운 형태다. 실제로 첫 확인에서 `cache_creation` 만 보고
"통과된다"고 판단할 뻔했다 — 2회차를 찍어 보고서야 read 가 0 인 것이 드러났다.

## 5. 남긴 것

| 항목 | 상태 |
| --- | --- |
| `cache_control` 전송 | **안 한다** (`GatewayVerificationClient`) |
| 회귀 테스트 | `프롬프트_캐싱을_쓰지_않는다` — 요청 본문에 `cache_control` 이 없음을 고정 |
| **usage 로깅** | **남긴다** — `in/out/cache_write/cache_read` 넷을 다 찍는다 |
| `FakeUpstream.lastRequestBody()` | 요청 본문 검사용으로 추가 |

🔴 **usage 로깅이 이번 판정을 가능하게 한 도구다.** 그 전에는 `content[0].text` 만 읽고
`usage` 를 버려서, 호출당 비용을 아는 방법이 **크레딧 잔액을 전후로 빼는 것뿐**이었다
(2026-09-20 에 실제로 그렇게 쟀다 — 110건 = 6,781 크레딧, 건당 61.6).

## 6. 다시 시도한다면

**먼저 `cache_read_input_tokens` 가 차는지부터 재고** 넣는다. GATEWAY 구성이 바뀌어 상위가
고정되면 성립할 수 있다.

캐싱 말고 남은 절감 수단(미검증):

- **후보를 묶어 한 호출로** — 호출 수가 1/5~1/10 로 줄고 반복 컨텍스트도 그만큼 준다.
  스키마가 배열로 바뀌어 `LlmVerifier` 계약 변경이 필요하다.
- **1차 필터를 소형 모델로** — 명백한 오답을 싸게 걸러내고 Sonnet 은 남은 것만.
- **후보 수 축소** (`embedding-top-k: 20` → 10) — 선형 감소, 재현율 하락.
