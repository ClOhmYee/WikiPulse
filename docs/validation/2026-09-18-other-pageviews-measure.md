## 2. 형식

```
project title count bytes      # 공백 4개, 헤더 없음
en !!!_(album) 1 0
en.m Air_India_Flight_171 268 0
```

- `project` 는 **도메인 약어**다. 일별 `pageview_complete` 의 `en.wikipedia` 와 코드 체계가 다르다.
- 데스크톱(`en`)과 모바일(`en.m`)이 **다른 행**으로 온다. 합치지 않으면 조회수가 갈린다.
- `bytes` 는 현재 전부 0 이라 쓰지 않는다.
- **시각 컬럼이 없다.** 시각은 파일명에서만 온다 — 파일과 시각을 잘못 짝지으면 조회수가
  통째로 다른 시간에 붙고 아무 에러도 안 난다. 적재 CLI 가 받은 파일명을 다시 읽어 대조한다.
- 🔴 **파일명 시각은 윈도우 끝이다. 시작이 아니다** (2026-09-21 정정, WP-127).
  `pageviews-20250612-090000.gz` 는 09시가 아니라 **08:00~09:00** 을 담는다. 처음엔
  시작으로 읽어서 모든 조회수가 한 시간 늦게 붙었고, 값이 그럴듯해 화면만 봐서는
  드러나지 않았다. 근거는 §6, 재현은 `ai/spec-evidence/pageview_hourly_offset.py align`.

약 22억 행이다. 2단계 계약에서 조회수를 봐야 하는 건 1단계(사람 편집 1건 이상)를 통과한
문서뿐이므로, 후보 제목 집합으로 거르는 것이 정상 경로다(`--titles`). 필터 없는 적재는
품질 측정·전수 비교용이다.

`en` 계열 project 는 16종이 있었다. `en.d`(wiktionary) 92,769행 · `en.s`(wikisource)
21,523행 등 자매 프로젝트가 섞여 있어, `en`·`en.m` 만 받는다. 넣으면 조회수가 부풀고
에러는 안 난다.

## 4. 제목 표기

- 공백은 밑줄이다. `canonical_title` 로 공백형에 맞춰 편집 덤프·LIVE 와 같은 키를 만든다.
- ⚠️ **percent-encoding 을 풀지 않는다.** `%` 가 든 행은 85건(조회수 264, 전체의 0.00%)
  뿐이었고 전부 `1%_rule`·`%s`·`%APPDATA%` 처럼 **문자 그대로의 퍼센트**였다. 디코드하면
  그런 제목이 오히려 깨진다.
- `_` · `__` 처럼 canonical 을 거치면 빈 문자열이 되는 행이 5건 있었다. 그대로 두면 제목이
  빈 `wiki_page` 행이 생기므로 버린다.

## 5. agent

이 덤프에는 agent 필드가 없다. 위키미디어가 감지한 봇·스파이더는 upstream 에서 이미
걸러 내지만(명세 §3.2 3번) 어느 agent 였는지는 노출하지 않는다.

~~"봇 구분이 없다"~~ → **upstream 에서 걸러지되 구분값이 없다** 가 정확한 서술이다
(WP-127 이슈 본문의 표현을 여기서 정정한다).

그래서 `PageviewHourly` 에는 agent 가 없고, 일별 `pageview_complete` 의 `agent=user` 와
값이 얼마나 다른지는 ~~아직 안 쟀다~~ → **첫 표본을 쟀다** (2026-09-21, §6).
`Air India Flight 171` 3구간에서 **차이 0 — 값이 비트 단위로 같다.**

⚠️ **표본 하나다.** 문서 1개·3구간이고, 봇 트래픽이 많은 문서(목록·리다이렉트 대상,
API 로 긁히는 문서)에서도 같으리라는 근거는 아직 없다. "차이가 없다"로 일반화하지
말고 후보 문서 여러 개로 다시 재는 것이 남았다 — `pageview_complete` 를 계속
보존하는 이유가 그 비교다.

## 6. 시간 정렬 실데이터 대조 (2026-09-21 추가, WP-127)

"파일명 시각은 윈도우 끝" 이 맞는지 **실제 두 소스를 맞대 확인**했다. 커밋
`de17cbd` 이 이 근거를 주장하면서도 재현 코드가 없었다 — 그걸 남긴다.

대상: `Air India Flight 171` (2025-06-12). 사고 08:09 UTC, 문서 생성 08:58:02 UTC.
프로파일이 3 -> 24,669 로 네 자리 튀어서 **한 칸만 밀려도 드러난다.**

```
py -3 ai/spec-evidence/pageview_hourly_offset.py align \
    --date 2025-06-12 --hours 8,9,10 --title "Air India Flight 171"
```

| 윈도우(UTC) | 시간별 파일 | 시간별 값 | 일별 같은 시간 | 일별 +1h | 판정 |
| --- | --- | ---: | ---: | ---: | --- |
| 08:00~09:00 | `-090000` | 3 | **3** | 24,669 | 일치 |
| 09:00~10:00 | `-100000` | 24,669 | **24,669** | 36,434 | 일치 |
| 10:00~11:00 | `-110000` | 36,434 | **36,434** | 39,767 | 일치 |

일별 프로파일(`agent=user`): 08시 3 · 09시 24,669 · 10시 36,434 · 11시 39,767 ·
12시 65,126 · 13시 66,593 · 14시 63,966 · 15시 60,773.

**두 가지가 한 번에 확인된다.**

1. 파일명 시각은 윈도우 **끝**이다. `-090000` 이 09시 값(24,669)이 아니라 08시 값(3)을
   담는다 — 문서가 08:58:02 에 생겼으니 08시 칸에 2분치 3회만 있는 게 맞다.
2. 시간별 덤프와 일별 `agent=user` 의 **값이 같다**(차이 0). §5 의 "얼마나 다른지 안 쟀다"
   에 대한 첫 표본이다. ⚠️ 문서 1개·3구간이라 일반화하지 않는다.

⚠️ **측정 중 실수 두 개** — 다음 사람이 같은 데서 막히지 않게 적는다.

- 덤프를 **병렬로 받으면 429** 다(4개 동시에서 2개가 429). 429 응답은 gzip 이 아니라
  HTML 이라 파일은 생기고 크기만 169 B 다 — "받았다"고 착각하기 좋다. 스크립트는
  직렬로 받고 매직바이트를 본다.
- `batch.pageview.aggregate` 에 하루 덤프를 그냥 흘리면 **끝나지 않는다.** (title, hour)
  를 dict 로 전부 누적하는데 키가 수천만 개다(25분 넘게 안 끝나 죽였다). 그 함수
  독스트링이 "검증 슬라이스용" 이라고 적어 둔 그대로다 — 제목을 먼저 거르고 넣는다.
