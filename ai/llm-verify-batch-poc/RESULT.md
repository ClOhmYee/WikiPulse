# LLM 검증 비용 실측 — 배치·모델 (WP-170)

- 실행일: 2026-09-21
- 스크립트: `measure.py` (오프라인 회계 + `--live` 실호출)
- 정답셋: `ai/matching-goldset/cases.py` (WP-39)
- 프롬프트: 단건은 프로덕션과 같은 `ai/llm-verify-poc/prompts/verify_system_v1.txt`,
  배치는 여기 `prompts/verify_batch_system_v2.txt` (v1 에서 출력만 배열로)
- 소모 크레딧: **약 3,700** 

**결론: `gpt-5.4-nano` 단건 채택.** Sonnet 단건 대비 **9.8배** 싸고, 정답 일치는
동률 이상이며, 오탐이 0 이고, 순서 민감도가 원천적으로 없다.

---

## 0. 왜 쟀나

검증이 LLM 비용의 90% 다. 후보 하나당 1회 호출이라 이슈 하나에 10~28회가 든다.
WP-165 실측 기준 하루 분량이 58k~160k 크레딧이었다. 자동 처리 비용을 줄일 필요가 있었다.

줄일 수단이 둘이라 **같은 입력으로 네 조합을 전부** 돌렸다.

---

## 1. 크레딧은 토큰 비례다 — 출력이 5배 비싸다

GATEWAY 단가 (토큰당, 2026-09-21 콘솔):

| 모델 | 입력 | 출력 |
| --- | --- | --- |
| `claude-sonnet-4-5-20250929` | 0.03 | **0.15** |
| `gpt-5.4-nano` | 0.004 | 0.01875 |

검산이 맞는다 — Milton 단건 `30,030×0.03 + 2,773×0.15 = 1,317`, 배치
`7,337×0.03 + 1,917×0.15 = 508`, 합 1,825 로 실제 소모와 일치.

🔴 **출력이 입력의 5배**다. 그래서 "공유 컨텍스트를 줄인다"는 배치의 이점이 생각보다
작다 — 입력을 76% 줄여도 출력은 후보 수만큼 그대로라 **크레딧 절감은 61%** 다.

⚠️ 소액 호출은 크레딧 델타가 0 으로 찍힌다(정수 반올림). 단가를 역산하려면 충분히 큰
페이로드로 재야 한다.

## 2. 네 조합 — Milton (후보 15개)

정답 9(strong 4·weak 5) + 노이즈 6.

| 조합 | 정답 일치 | 오탐(FP) | 누락(FN) | 크레딧 |
| --- | --- | --- | --- | --- |
| Sonnet 단건 | 12/15 | **3** (MNST·KO·PG) | 0 | 1,317 |
| Sonnet 배치 **정순** | **14/15** | 0 | 1 (DUK) | 508 |
| Sonnet 배치 **역순** | 10/15 | 3 | 2 | 524 |
| **nano 단건** | 12/15 | **0** | 3 (GNRC·ETN·UAL) | **134** |
| nano 단건 + GDELT | 11/15 | 2 (MNST·KO) | 2 | ~150 |
| nano 배치 | 7/15 | 0 | 8 | 41 |

### 🔴 Sonnet 배치의 14/15 는 순서 덕이다

정순은 **정답 9개가 앞, 노이즈 6개가 뒤**였다 — 정답셋의 `answers + noise` 순서를
그대로 쓴 결과다. 순서만 뒤집자 **14/15 → 10/15** 로 떨어졌고, 단건(12/15)보다도
나빠졌다.

모델이 뒤로 갈수록 엄격해지는 경향이 있으면 "정답이 앞에 몰린" 순서에서 자동으로
만점에 가까워진다. **그 값을 배치의 실력으로 읽으면 안 된다.**

⚠️ 실전 후보 순서는 `BOTH → GDELT_ONLY → EMBEDDING_ONLY` 라 강한 후보가 앞에 온다.
정순에 가깝긴 하지만, 그건 가정이지 측정이 아니다.

### nano 배치는 Milton 에서만 무너진다

CrowdStrike 12/14 · PayPal 7/7 로 멀쩡했고 Milton 에서만 8개를 놓쳤다. 후보가 많고
정답 다수가 weak 인 sector 이슈에서 무너진다. 🔴 **모델 다운그레이드와 배치를 같이
적용하지 않는다** — 따로는 둘 다 이득인데 합치면 깨진다.

## 3. nano 단건 — `SINGLE_COMPANY_EVENT` 에서 경쟁사 게이트가 작동한다

소형 모델이 제일 깨지기 쉬운 지점이라 따로 쟀다. -45 가 `issue_class` 게이트를 넣은
이유가 "경쟁사를 배경지식만으로 통과시키는" 오탐 차단이다.

| 사례 | 유형 | nano 단건 | 오탐 |
| --- | --- | --- | --- |
| Milton | SECTOR_OR_REGION | 12/15 | 0 |
| CrowdStrike | **SINGLE_COMPANY** | **13/14** | 0 |
| PayPal | **SINGLE_COMPANY** | **7/7** | 0 |
| 합계 | | **32/36 (88.9%)** | **0** |

실제로 걸러낸 경쟁사:

- CrowdStrike 이슈 — `PANW`·`FTNT`(보안 경쟁사), `AAL`·`UAL`(DAL 과 같은 항공업)
- PayPal 이슈 — `V`·`MA`·`ADYEY`(결제 경쟁사)

`issue_class` 도 두 기업형 사례에서 `SINGLE_COMPANY_EVENT` 로 정확히 분류했다.

### 누락 4건은 전부 설명된다

- **DAL** (CrowdStrike) — 명세 §11 이 기록한 **GDELT 가 데려오는 2차 효과 정답**이다.
  이 실행은 GDELT 컨텍스트를 비웠다. 이슈 본문만으로는 델타항공이 안 나온다.
- **GNRC·ETN·UAL** (Milton) — 간접 노출. 보수적으로 잘렸고, GDELT 를 넣자 GNRC·ETN 이
  회복됐다(§4).

**36건 중 오탐 0** 이 핵심이다. Sonnet 단건은 같은 Milton 에서 코카콜라·P&G·몬스터를
허리케인에 붙였다. 투자 정보 피드에서 무관한 종목이 "관련"으로 노출되는 것이 못 잡는
것보다 나쁘다.

---

## 4. ⚠️ GDELT 컨텍스트는 양날이다

Milton 에 실측 기관명을 넣고 nano 단건을 다시 돌렸다.

| | 정답 잡음 | 오탐 | 합 |
| --- | --- | --- | --- |
| GDELT 없음 | 6/9 | 0 | 12/15 |
| GDELT 있음 | 7/9 | **2** | 11/15 |

`generac` 이 컨텍스트에 있으니 GNRC 를 잡았다 — 의도대로다. 그런데 동시에
몬스터·코카콜라를 `REGION` 으로 통과시켰다. **컨텍스트가 풍부해지자 전반적으로
관대해졌다.**

프롬프트로 조일 여지가 있다 — 컨텍스트를 "관련성 증거"가 아니라 "참고 목록"으로
명시하는 식. 아직 안 해봤다.

**기관명 출처**: `ai/gkg-alias-poc/RESULT.md` 의 실 GKG 별칭표(Milton 16슬롯, 코퍼스
26,910) + 명세 §11 의 `generac`·`publix`. ⚠️ **완전한 top-15 가 아니다** — 저장된 건
"별칭이 필요했던 14건"이라 직접 매칭된 기관이 빠져 있다. 지어낸 이름은 없다.

## 6. 재지 못한 것

- **nano 단건 + GDELT 를 `SINGLE_COMPANY_EVENT` 에서** 안 쟀다. GDELT 기관명에 경쟁사가
  섞이면 게이트가 뚫릴 수 있다. ⚠️ **측정 불가** — CrowdStrike 의 실 GKG 기관명이
  저장돼 있지 않고, 명세 §11 이 기업형 이슈는 GDELT 가 원인 제공자를 16시간 뒤에도
  4.5% 밖에 못 잡는다고 기록한다. 실전에서 기업형은 컨텍스트가 거의 비어 있어 위험이
  작다고 **추정**하지만 확인은 아니다.
- **배치 무작위 순서.** 정순·역순만 쟀다. 편향 없는 배치 정확도는 모른다.
- **사례 3건뿐이다.** 은행위기·IBM 은 안 돌렸다.
- **재시도·스키마 실패율.** 이번 실행에서 파싱 실패 0 이었지만 표본이 작다.
- **속도.** nano 가 "밀리초 응답"을 표방하는데 실측 안 했다. 워커 처리량에 영향이 있다.

## 7. 구현할 때 주의

- 🔴 **응답을 순서로 매칭하지 않는다.** 배치를 나중에 다시 보더라도, 모델이 N 개 중
  N-1 개만 돌려주면 마지막 판정이 엉뚱한 티커에 붙는다 — 에러 없이 조용히 오배정된다.
  티커로 찾는다.
- 🔴 **OpenAI 경로는 API 모양이 다르다.** Anthropic 은 `system` 이 별도 필드이고 사용량이
  `usage.input_tokens`, OpenAI 는 system 이 메시지 배열의 첫 항목이고 `usage.prompt_tokens`
  다. 한쪽 모양으로 다른 쪽을 부르면 **빈 응답이 조용히 온다.**
- 🔴 **nano 계열은 추론 토큰을 먼저 먹는다.** `max_completion_tokens` 를 넉넉히 주지
  않으면 본문이 빈 문자열로 온다 — 에러가 아니다. 이 스크립트는 단건 상한의 4배를 준다.
- ⚠️ **모델을 바꾸면 `prompt_version` 재검토가 필요하다** — `verify_system_v1.txt` 는
  Sonnet 으로 실측된 계약이다(-45). 그리고 기존 판정 재사용이 무효화된다. 현재 운영
  검증 통과가 3건뿐이라 **지금이 가장 싸다.**

## 재현

```bash
# 오프라인 (크레딧 0)
python ai/llm-verify-batch-poc/measure.py --case Milton

# 실호출 — 🔴 크레딧을 쓴다. .env 의 LLM_GATEWAY_KEY 를 읽는다
python ai/llm-verify-batch-poc/measure.py --case Milton --live --model gpt-5.4-nano
python ai/llm-verify-batch-poc/measure.py --case CrowdStrike --live --model gpt-5.4-nano
python ai/llm-verify-batch-poc/measure.py --case Milton --live --batch-only --reverse
```

판정은 `result-<사례>-<모델>-<순서>-<시각>.json` 으로 남고 **커밋한다**. ⚠️ 실호출은
크레딧을 쓰므로 결과를 화면에만 두지 않는다 — 2026-09-21 에 배치 단독 실행에서 판정을
출력하지 않아 524 크레딧을 쓰고 결과를 못 본 적이 있다.

⚠️ 입력 재료(위키 도입부·yfinance 사업설명)는 `cache.json` 에 캐시한다. 매 실행마다
다시 받으면 **다른 입력을 비교하게 된다.** 그리고 WP-164 수집이 같은 IP 의
`api.php` 예산을 쓰고 있어 캐시 없이는 429 를 맞는다.
