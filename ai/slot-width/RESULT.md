## 왜 쟀나

WP-84 가 슬롯을 `hour_of_week`(168) → `hour_of_day`(24)로 바꿔 "28일 창에 최대
4관측" 을 고쳤다. 그런데 `Boeing_787_Dreamliner`(2011년 생성, 월 197편집)가 여전히
`is_new_page=True` 로 판정됐다 — 24슬롯도 얇은 것 아닌가.

## 1. 분포 — 얇은 게 맞다

월 20편집 이상 문서 기준, 28일 창:

| 슬롯 | 슬롯당 `sample_days>=7` | 문서 중 1개라도 통과 |
| --- | --- | --- |
| **1h (24) — 현재** | **1.5% / 1.4%** | **4.8% / 4.7%** |
| 3h (8) | 5.4% / 5.4% | 13.7% / 14.0% |
| 6h (4) | 13.0% / 13.5% | 25.2% / 26.9% |
| 일 (1) | 58.1% / 60.2% | 58.1% / 60.2% |

앞이 2025-06, 뒤가 2024-10. **두 달이 1pp 이내로 일치**한다(대상 13,500 / 13,624 문서).

편집 수 분포가 극단적으로 치우쳐 있다 — 2025-06 창 안 문서 1,059,567개 중 **1편집이
628,999개**, 100편집 이상은 878개뿐이다.

월 편집 수 구간별(1h, 2025-06):

| 월 편집 | 1개 슬롯이라도 통과 |
| --- | --- |
| 20~49 | **0.8%** |
| 50~99 | 8.2% |
| 100~299 | 39.9% |
| 300~999 | 83.3% |

**24슬롯 z 경로는 사실상 월 300편집 이상 문서 전용**이다.

## 2. 임계를 낮추는 건 답이 아니다

1h 슬롯에서 문서 중 1개라도 통과하는 비율:

```
sample_days>=3  50.1%    >=4  24.3%    >=5  12.8%    >=6  7.6%    >=7  4.8%
```

7 → 5 로 내려도 12.8% 다. 절반을 넘기려면 3까지 내려야 하는데, 그건 3일치 관측으로
표준편차를 믿는 것이다. **선택지 3번 탈락.**

## 3. 넓히면 무엇을 잃나

같은 관측에 1h·6h 기준선을 각각 물려 `edit_z` 를 비교했다 (2025-06, 월 100편집 이상 965문서):

| | 값 |
| --- | --- |
| 판정 대상 윈도우 | 2,134 |
| z 경로 가능 | 1h **482 (23%)** → 6h **1,726 (81%)** |
| 둘 다 가능한 구간 | 479 윈도우 |
| 임계 판정 일치 | **469 (97.9%)** |
| 불일치 | 10건 — 1h만 급증 7 · 6h만 급증 3 |
| z 차이 (6h − 1h) | 중앙값 +0.07 · 평균 −0.10 · 범위 −11.53 ~ +1.69 |

겹치는 구간에서는 거의 같은 답을 내고, 안 겹치던 1,244 윈도우가 z 경로로 들어온다.
여기까지는 "넓히는 게 낫다" 로 읽힌다.

## 🔴 4. 그런데 좋아지는 게 없다

`SLOT_HOURS` 를 실제로 바꿔 -85 회귀를 돌렸다:

| | 1h (현재) | 6h |
| --- | --- | --- |
| 재현율 | 10/12 | **10/12** |
| 대조군 오탐 | 49건 | **49건** |
| 대상 급증 건수 | — | 거의 동일 (Helene 32 → 31) |
| -86 사건 10건 | — | **완전 동일** |

폭을 2·3·4·6·12h 로 쓸어봐도 오탐은 **42~51 범위의 잡음**이고 방향이 없다.

**원인**: `Deaths_in_2024` 오탐 23건 중 **21건이 z 경로를 통과한다.** 상시 편집 목록
문서는 자기 기준선 대비로도 진짜로 튄다 — z 를 살려도 안 걸린다. 오탐의 원인은
"z 가 죽어서" 가 아니었다.

## 🔴 5. 발단이던 예시는 슬롯 문제가 아니었다

`Boeing_787_Dreamliner` 의 **사건 전 28일** 관측:

```
1h 슬롯 최대 sample_days 2   ·   6h 최대 2   ·   일 최대 5
```

편집이 있었던 날이 **5일뿐**이다. 일 단위 슬롯(1개)으로도 7 에 못 미친다.
**"슬롯이 좁아서" 가 아니라 "그 문서가 평소에 거의 안 고쳐져서"** 였다.
그 달 197편집은 대부분 사건 당일 이후에 몰려 있었다.

## 왜 안 바꿨나 (2026-09-15 결정)

측정 가능한 개선이 없다. 남는 건 구조 교정 하나 — 죽어 있던 `EDIT_Z_THRESHOLD` 가
실제로 돈다는 것뿐이다. 그 대가가 작지 않다:

- **V5 마이그레이션이 팀 전원 부담**이다. 같은 날 V4 도 나갔다 — 한 번에 둘을 떠넘기게 된다
- `hour_of_day` → `slot_index` 개명이 **19개 파일**을 건드린다. HDFS 재생성 후속
  (`-56`·`-57`, MR !50)이 같은 배치 경로라 충돌 면적이 넓다
- **선택지 4번을 할 때 슬롯 의미를 어차피 다시 본다.** 신규/기존 경로를 쪼개면
  "얇은 기존 문서" 를 어떤 기준선으로 볼지가 핵심이다. 지금 6h 로 못 박으면 그때 V6 를
  또 파야 한다 — 마이그레이션 두 번보다 한 번이 낫다

⚠️ **다음 사람이 빠질 함정**: `EDIT_Z_THRESHOLD = 3` 은 선언돼 있지만 판정 대상
윈도우의 23% 에서만 돈다. 이 값을 튜닝하고 아무 변화가 없어도 코드가 고장 난 게 아니다.

구현은 브랜치 `feature/WP-88-slot-width` 에 남아 있다(MR !56, 머지 안 함).
선택지 4번을 할 때 그대로 꺼내 쓴다.
